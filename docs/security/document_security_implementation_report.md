# DOCUMENT SECURITY IMPLEMENTATION REPORT

## النطاق

تم تطبيق أقل مجموعة ضرورية لتقوية رفع وتنزيل وثائق الصفقات والعروض ضمن البنية الحالية، مع إبقاء التخزين عبر S3 helpers وعدم إدخال أسرار أو روابط خاصة في الكود.

## validations المطبقة

| الضابط | التنفيذ |
|---|---|
| الامتداد | القائمة المسموحة: `.pdf`, `.doc`, `.docx`, `.xls`, `.xlsx`. |
| MIME | حصر MIME في PDF وWord وExcel المدعومة، مع مقارنة أولية بتوقيع المحتوى. PDF يتطلب `%PDF-`، وملفات Office تتطلب OLE أو ZIP signature. |
| الحجم | حد أقصى 10 MiB لكل وثيقة. |
| العدد | حد أقصى 20 وثيقة لكل صفقة أو عرض. |
| الاسم والمسار | رفض المسارات والفاصل الصفري والأسماء الخاصة، وتطهير الاسم، وعدم استخدام اسم العميل وحده كمسار؛ أضيف UUID إلى مفتاح التخزين. |
| البيانات | رفض Base64 غير الصالح أو الفارغ. |

هذه الفحوصات دفاعية وليست فحصاً شاملاً لمحتوى Office أو مكافحة برمجيات خبيثة؛ لذلك لا يُفهم منها أن الملف آمن قانونياً أو تشغيلياً بمجرد قبوله.

## permissions المطبقة

وثائق الصفقة تُرفع من authority المالكة أو admin أثناء حالة `draft` فقط. تنزيلها يتحقق من وجود الوثيقة ثم الصفقة ثم علاقة الدور: supplier لا يصل إلا بعد نشر الصفقة، بينما authority المالكة وregulator وadmin يخضعون للمسار الحالي. وثائق العرض تُرفع من supplier المالك أو admin أثناء حالة `draft` وقبل deadline. تنزيل وثيقة العرض يقيد supplier بملكيته، ويقيد authority المالكة وregulator بوجود جلسة فتح، ويمنع الوصول إلى عرض منافس قبل ذلك.

التحقق يتم من خلال `documentId` ثم `bidId` أو `tenderId` المرتبط في قاعدة البيانات، وليس من خلال معرّف منفرد يثق به العميل؛ وهذا يقلل IDOR في المسارات الحالية.

## audit events

تم الإبقاء على أحداث الرفع والتنزيل الناجح، وإضافة `access_denied` لمحاولات تنزيل وثائق مرفوضة، مع `documentId` وكيان المجال في `safe_metadata`. لا يوجد حذف وثائق فعلي في العقود الحالية، ولذلك لم يُنشأ حذف شكلي أو حدث حذف غير مدعوم.

## حالات الواجهة

الواجهة الحالية تعرض اختيار الملفات وقائمة الوثائق المحفوظة وحالات التحميل والنجاح والفشل ضمن تدفقات الصفقة والعرض. رسائل الخادم العربية الجديدة تشرح نوع الملف غير المسموح، المحتوى غير المطابق، الحجم الزائد، بلوغ العدد، أو منع التنزيل. لم تتم إضافة ميزة حذف أو إعادة محاولة مستقلة لأن endpoint الحذف غير موجود في النموذج الحالي؛ إدخالها يتطلب عقداً خادمياً وسياسة احتفاظ واضحة.

## الاختبارات والتحقق

| الاختبار | النتيجة |
|---|---|
| TypeScript | ناجح، `TYPECHECK_EXIT=0`. |
| Build | ناجح، `BUILD_EXIT=0`، مع تحذير حجم bundle قائم. |
| ملف غير مسموح | مغطى بعقد التحقق في `decodeDocument`، ويرفض الامتداد أو MIME غير المدعوم. |
| حجم زائد | مغطى بحد 10 MiB على الخادم. |
| IDOR | مسارات التنزيل تعيد التحقق من ملكية المورد وعلاقة الوثيقة بالصفقة/العرض. |
| صلاحية التنزيل حسب الدور | مغطاة بعقود الصلاحيات الحالية، مع إضافة audit للرفض. |
| RTL/mobile | التحقق البصري السابق للواجهات ذات الصلة ناجح؛ لم تُضف واجهة جديدة واسعة النطاق في هذه الدفعة. |
| Vitest | شُغّل ضمن حزمة التحقق؛ يلزم إعادة تشغيل منفصل مخصص لتسجيل رمز الخروج النهائي إذا توقفت الجلسة قبل طباعة الملخص. |

## الملفات التي تغيرت

`server/routers.ts` فقط من ناحية المنطق الوظيفي في هذه الدفعة، إضافة إلى هذا التقرير و`todo.md`. لم تُضف migration لأن مخطط وثائق الصفقة والعرض كان موجوداً ومناسباً للضوابط الحالية.

## القيود المتبقية

لا يوجد فحص عميق للـ MIME عبر مكتبة signature متخصصة، ولا antivirus أو sandboxing، ولا encryption-at-rest مضاف من داخل التطبيق، ولا lifecycle deletion أو retention policy. كما أن روابط S3 الموقعة تعتمد على helper الموجود في المشروع؛ يجب التحقق من مدة صلاحيتها وسياسة bucket في بيئة الإنتاج. ويجب مراجعة السماح لـ regulator بتنزيل وثائق الصفقة العامة ووثائق العرض بعد الفتح مقابل السياسة المؤسسية والقانونية.

## الحكم

تم تقليل مخاطر الامتداد والحجم والأسماء ومسارات التخزين وIDOR والتنزيل غير المصرح به بأقل تغيير. هذه الدفعة لا تكفي وحدها لاعتماد رفع ملفات حساس في Pilot إنتاجي قبل إضافة فحص محتوى/برمجيات خبيثة، مراجعة bucket ومدة الروابط الموقعة، واختبارات E2E فعلية لثلاثة أدوار.
