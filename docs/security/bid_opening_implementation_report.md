# BID OPENING IMPLEMENTATION REPORT

## نطاق التنفيذ

تم تنفيذ مرحلة **Electronic Bid Opening / فتح العروض المغلقة** ضمن البنية الحالية لمنصة «صفقات ذكية»، مع الالتزام بوقت الخادم، وحماية الوصول قبل الفتح، وقيد الملكية للمصلحة المتعاقدة، ومنع تكرار جلسة الفتح، وتسجيل العمليات الحساسة في سجل التدقيق. لم يتم توسيع النطاق إلى التقييم أو الإرساء أو التوقيع القانوني أو التشفير الادعائي.

## تدفق الفتح الفعلي

1. يرسل المتعامل الاقتصادي العرض نهائياً، وتبقى حالته `submitted`/`sealed` وفق الحالة المدعومة في النموذج الحالي، ولا يصبح محتواه متاحاً للقراءة العامة أو للمصلحة المتعاقدة قبل الفتح.
2. تستدعي بوابة المصلحة المتعاقدة إجراء `bidOpening.eligibility` المحمي بالخادم. يعيد الإجراء حالة جلسة مشتقة من وقت الخادم، مثل `before_opening` أو `opening_available` أو `already_opened` أو `no_submitted_bids`، دون كشف محتوى العروض قبل الأجل.
3. لا يُسمح بالفتح إلا للمستخدم `authority` الذي يملك الصفقة أو للمستخدم `admin`. تم عزل `regulator` عن جلسة الفتح في النسخة الحالية، ولا يملك تنفيذ العملية.
4. بعد بلوغ وقت الفتح المحدد، يستدعي المستخدم `bidOpening.open`. يعيد الخادم التحقق من الصفقة والصلاحية ووقت الخادم وعدد العروض، ثم ينشئ جلسة فتح واحدة ويحدّث العروض المقدمة فقط إلى الحالة المفتوحة مع `openedAt`.
5. تُحفظ بيانات محضر الفتح server-side ضمن جلسة فريدة لكل صفقة، وتُعرض في واجهة جلسة الفتح. إعادة استدعاء العملية بعد نجاحها لا تنشئ جلسة ثانية ولا تعيد فتح العروض بلا ضوابط.

## RBAC verification

| العملية | المورد | regulator | admin | المصلحة المالكة | مورد آخر |
|---|---:|---:|---:|---:|---:|
| قراءة أهلية الفتح | مرفوض | مرفوض | مسموح | مسموح | مرفوض |
| تنفيذ الفتح | مرفوض | مرفوض | مسموح | مسموح | مرفوض |
| قراءة تفاصيل العرض قبل الفتح | مرفوض | مرفوض | مقيدة بحسب الإجراء | مرفوضة | مرفوضة |
| تغيير العرض بعد الإرسال النهائي | مرفوض | مرفوض | مرفوض بحسب انتقالات العرض | مرفوض | مرفوض |

التحقق الفعلي يتم في إجراءات tRPC المحمية، وليس بواسطة إخفاء الزر في الواجهة. الواجهة تعكس حالة الخادم فقط، ولا تُستخدم كحاجز أمني نهائي.

## اختبار قبل الموعد وبعده

تم تضمين تحقق خادمي صريح يقارن وقت الخادم بموعد الصفقة، مع حالة `before_opening` قبل الموعد وحالة `opening_available` بعده. لا تستخدم واجهة الجلسة `Date.now()` لاتخاذ قرار السماح. قرار الفتح النهائي داخل إجراء الخادم.

## اختبار محاولة الوصول المباشر إلى API

تمت تغطية عقد حماية إجراءي الأهلية والتنفيذ واختبار وجود `FORBIDDEN` و`PRECONDITION_FAILED` ومسارات `bid_opening_denied`. كما تم تثبيت عزل `regulator` في نطاق Bid Opening باختبار عقدي. يلزم قبل Pilot إضافة اختبار تكاملي مصادق عليه يرسل طلباً فعلياً إلى API بهويات الأدوار المختلفة؛ الاختبار الحالي يثبت عقود المصدر والبنية، وليس بديلاً عن E2E كامل.

## اختبار إعادة المحاولة وIdempotency

تدعم جلسة الفتح قيداً فريداً لكل `tenderId`، وتتحقق طبقة قاعدة البيانات من حالة الجلسة السابقة قبل إنشاء جلسة جديدة. لذلك لا تُنشأ جلسة فتح ثانية لنفس الصفقة من خلال إعادة الضغط أو إعادة الطلب. يلزم اختبار تنافسي على اتصالين متزامنين قبل اعتماد الإنتاج للتحقق من سلوك السباق على قاعدة البيانات المستهدفة.

## محتويات محضر الفتح

محضر الفتح المحفوظ يتضمن، ضمن البيانات المتاحة فعلياً:

- معرف الصفقة ورقمها الداخلي.
- عنوان الصفقة.
- وقت الفتح الذي يحدده الخادم.
- عدد العروض المستلمة القابلة للفتح.
- قائمة العروض التي انتقلت إلى الحالة المفتوحة مع معرفاتها وأوقات فتحها.
- هوية المنفذ وفق المستخدم المصادق عليه وسجل التدقيق.
- حالات الرفض أو عدم وجود عروض أو إعادة المحاولة المهمة.

المحضر قابل للعرض من خلال عقد جلسة الفتح وواجهة authority. **تصدير المحضر إلى PDF أو ملف رسمي ليس منفذاً في هذه المرحلة**، كما لم تتم إضافة توقيع قانوني أو ختم زمني موثّق خارج سجل النظام.

## Audit events

تمت إضافة أو ربط الأحداث التالية في مسارات الفتح:

| الحدث | متى يسجل |
|---|---|
| `bid_submitted` | عند الإرسال النهائي للعرض، وفق مسار العرض الحالي |
| `bid_opening_attempted` | عند محاولة طلب تنفيذ الفتح |
| `bid_opening_denied` | عند الرفض بسبب الصلاحية أو الوقت أو الحالة أو عدم وجود عروض |
| `bid_opened` | عند نقل العرض المرسل إلى الحالة المفتوحة |
| `opening_minutes_generated` | عند إنشاء بيانات محضر جلسة الفتح |

تُسجل الأحداث عبر مسار `logAudit` الحالي مع الفاعل ونوع الكيان ومعرفه والنتيجة والبيانات الآمنة المتاحة. لا يتضمن التنفيذ ادعاء عدم قابلية السجل للتغيير خارج الضمانات التي توفرها قاعدة البيانات الحالية.

## الملفات المتغيرة

- `drizzle/schema.ts`: إضافة `openedAt` للعروض وجدول جلسة فتح فريدة لكل صفقة ومحضرها server-side.
- `drizzle/0003_empty_stellaris.sql`: migration غير هدّامة مطبقة على قاعدة البيانات.
- `server/db.ts`: استعلامات أهلية الفتح وإنشاء/قراءة جلسة الفتح وفتح العروض المرسلة فقط.
- `server/routers.ts`: إجراءات `bidOpening.eligibility` و`bidOpening.open` وحماية بيانات العروض وسجل التدقيق وعزل الأدوار.
- `client/src/pages/AuthorityShell.tsx`: واجهة جلسة فتح العروض وحالات قبل الموعد والمتاح والمفتوح وعدم وجود عروض والفشل.
- `server/core-procurement-flow.test.ts`: اختبارات عقود جلسة الفتح والوقت الخادمي وRBAC ومحضر الفتح وعدم استخدام وقت العميل.
- `todo.md`: تحديث حالة بنود تنفيذ Bid Opening.
- `bid_opening_security_implementation_plan.md`: الخطة الأمنية والتنفيذية المرجعية.

## النواقص المتبقية

لا توجد حالياً آلية تكاملية كاملة لاختبار مستخدم authority ومستخدم supplier عبر جلسات OAuth فعلية داخل المتصفح. كما لا يوجد تصدير رسمي للمحضر، ولا نموذج مستقل لأعضاء لجنة فتح متعددين، ولا توقيع إلكتروني، ولا تشفير مجال موثق للعروض خارج آليات الحالة والصلاحيات الحالية. هذه العناصر لا ينبغي تمثيلها كقدرات قانونية مكتملة.

## مخاطر Pilot والمراجعة القانونية المطلوبة

قبل Pilot محدود، يجب تنفيذ اختبار API تكاملي مباشر بمستخدمين منفصلين، واختبار تزامني لإعادة الطلب، والتحقق من سياسات النسخ الاحتياطي وقابلية استرجاع جلسات الفتح. يلزم كذلك مراجعة قانونية لتحديد ما إذا كان محضر النظام الحالي يفي بمتطلبات محضر فتح رسمي، وما إذا كانت هوية المنفذ ووقت الخادم وحفظ السجل كافية إثباتياً. لا يجوز تسويق المحضر الحالي كتوقيع إلكتروني أو سجل غير قابل للتلاعب دون طبقة قانونية وتقنية إضافية.

## الحكم التنفيذي

المرحلة أصبحت **مطبقة تقنياً على مستوى MVP داخلي**: الإنفاذ الأساسي للوقت والصلاحية والتكرار وسجل التدقيق موجود، والواجهة تعرض الحالات الأساسية. لكنها ليست بعدُ بديلاً عن اختبار تكاملي مصادق عليه أو مراجعة قانونية لمحضر الفتح قبل تشغيلها في Pilot فعلي للمشتريات العمومية.
