# RBAC & AUDIT IMPLEMENTATION REPORT

## نطاق التنفيذ

تم تنفيذ مراجعة وتصحيح محدودين لـ **RBAC + Audit Trail** في البنية الفعلية للمشروع، التي تستخدم React/Vite وExpress/tRPC وDrizzle/MySQL/TiDB. لم تُغيّر أسماء الأدوار أو نموذج الهوية. التسمية الفعلية في الكود هي `supplier` و`authority` و`regulator` و`admin`، مع بقاء `economic_operator` و`contracting_authority` و`central_administration` كتسميات وظيفية مقابلة في الوثائق فقط.

## ما تم تصحيحه

تم إغلاق ثغرة التعيين الذاتي للأدوار الحساسة؛ فلا يستطيع المستخدم العادي تعيين نفسه `authority` أو `regulator`. تُرفض المحاولة من الخادم، وتُسجل المحاولة الحساسة بنتيجة الرفض. بقي تعيين `supplier` مسموحاً وفق النموذج الحالي لأنه لا يمنح صلاحية إدارية، ولم يُضف أي مسار ترقية ذاتية إلى `admin`.

تمت إضافة `actorRole` إلى `AuditLog` عبر migration غير هدّامة، مع تعبئته من دور المنفذ الحالي. أصبحت دالة `logAudit` المركزية تضيف الدور من الخادم وتقوم بتنقية metadata من مفاتيح الأسرار الشائعة مثل كلمات المرور والرموز والمفاتيح والكوكيز وAuthorization. لا تُسجل كلمات المرور أو tokens أو محتوى الوثائق الحساسة. لا يدعم `TrpcContext` الحالي request/correlation ID، ولذلك لم يُدّعَ تسجيله.

تم الحفاظ على عزل الكيانات الموجود فعلياً: إجراءات الصفقة تعتمد على `authorityId`، وإجراءات العروض تعتمد على `supplierId`، وتنزيل الوثائق يتحقق من علاقة الوثيقة بالصفقة أو العرض ومن صلاحية المستخدم قبل إصدار الرابط الموقّع. إجراءات فتح العروض والتقييم والإسناد محمية بدور authority وبعلاقة الصفقة عند الحاجة. رؤية سجل التدقيق محصورة في `regulator` و`admin` عبر الخادم.

## مصفوفة الصلاحيات الفعلية

| المورد | supplier | authority | regulator | admin |
|---|---|---|---|---|
| الصفقات المنشورة | قراءة عامة عبر الإجراء المنشور | قراءة وإدارة صفقاته | قراءة مراقبة | صلاحيات الإدارة المتاحة في الإجراء |
| إنشاء/تحديث/نشر الصفقات | ممنوع | مسموح لمالك الصفقة وبالحالات المسموحة | ممنوع | بحسب إجراءات admin الحالية؛ لا يوجد bypass عام موثق لكل إجراء |
| العروض الخاصة به | إنشاء/تحديث/إرسال لمسوداته | لا يقرأ تفاصيل عروض المنافسين قبل الفتح | قراءة مراقبة بحسب الإجراء | بحسب الإجراء |
| عروض متعامل آخر | ممنوع object-level | ممنوع قبل الفتح أو خارج العلاقة | لا يوجد وصول عام إلى payload الحساس | بحسب الإجراء الموثق |
| وثائق الصفقة | تنزيل ما تسمح به حالة النشر والصلاحية | رفع وثائق صفقاته وتنزيل المسموح | بحسب صلاحية القراءة الحالية | بحسب الإجراء |
| وثائق العرض | إدارة وثائقه فقط | لا يرى محتوى العرض قبل الفتح | بحسب حدود الإجراء | بحسب الإجراء |
| جلسات الفتح | ممنوع التنفيذ | تنفيذ الفتح للصفقة المخولة | ممنوع التنفيذ؛ قراءة المراقبة فقط حيث يدعم الإجراء | وفق الإجراء الحالي |
| التقييم والإسناد | ممنوع | مسموح للمصلحة المخولة | ممنوع mutation | بحسب الإجراء |
| التحليلات | ممنوع من regulator procedures | ممنوع | قراءة overview/stats | قراءة الإدارة المتاحة |
| Audit logs | ممنوع | ممنوع | قراءة | قراءة |
| بيانات الملف الشخصي | قراءة/تحديث ملفه | قراءة/تحديث ملفه | قراءة/تحديث ملفه | وفق الإجراء |

هذه المصفوفة تصف العقود الحالية ولا تعني وجود قدرات غير موجودة. أي خلية تعتمد على “بحسب الإجراء” لا ينبغي تفسيرها كصلاحية شاملة غير مقيّدة.

## التحقق من API وIDOR

| الاختبار | النتيجة |
|---|---|
| وصول غير مصادق إلى protected procedures | ناجح: `UNAUTHORIZED` |
| supplier إلى bid أو payload خاص بمورد آخر | محمي بعقود الدور والملكية؛ اختبار الوصول المباشر إلى `bids.forTender` مرفوض |
| authority إلى tender غير مملوك | ناجح في اختبارات update/publish: `NOT_FOUND` |
| regulator إلى mutations التعاقدية | ناجح: `FORBIDDEN` |
| الوصول المباشر للـAPI دون المرور بالواجهة | مغطى عبر `createCaller` المباشر في Vitest |
| تنزيل وثيقة بتبديل document/bid/tender IDs | تتحقق endpoints من علاقة الكيان والملكية قبل إصدار الرابط؛ تغطية IDOR التفصيلية للملفات ما زالت مطلوبة كاختبار E2E مستقل |
| رؤية سجل التدقيق | supplier وauthority مرفوضان؛ regulator وadmin مسموحان |
| التعيين الذاتي إلى authority/regulator | مرفوض خادمياً |

## Audit events

الأحداث الحساسة الحالية تتضمن أحداث دورة الصفقة والعروض والوثائق والفتح، إضافة إلى `role_assigned` و`role_assignment_denied` الناتجين عن مسار تعيين الدور. يسجل السجل المركزي `actorId` و`actorRole` و`action` و`entityType` و`entityId` و`result` و`metadata` ووقت الخادم. تظل أسماء الأحداث الموجودة في المسارات الأخرى كما هي للحفاظ على التوافق.

## الاختبارات المنفذة

## القيود المتبقية

لا يوجد request/correlation ID في `TrpcContext` الحالي، ولذلك لا يضيفه AuditLog. لا توجد middleware عامة للـobject-level permissions؛ الحماية موزعة داخل الإجراءات، ما يزيد خطر التراجع مستقبلاً. ما زالت هناك حاجة إلى اختبار E2E مصادق عليه يغطي كل مسارات تنزيل الوثائق وتبديل المعرفات بين الأدوار.

لم تُضف صلاحيات إدارية خاصة غير موجودة في النموذج، ولم تُفتح صلاحيات regulator mutation. كما لم تُسجل أي أسرار أو محتوى وثائق في metadata. يلزم قبل Pilot مستقل مراجعة كل إجراء جديد عند إضافته مقابل هذه المصفوفة، ومراجعة قانونية/حوكمية لسياسة الاحتفاظ بسجلات التدقيق.

## الحكم

تم إغلاق الفجوات المؤكدة في **التعيين الذاتي للأدوار الحساسة** وتوحيد الحد الأدنى من هوية Audit Trail. ما يزال النظام بحاجة إلى اختبارات E2E للـIDOR والملفات، وإلى إدخال correlation ID مركزي إذا أصبح مطلوباً تشغيلياً، قبل اعتبار RBAC وAudit جاهزين لإطلاق تجريبي مضبوط.
