# نموذج تهديد تشفير عروض المتعاملين

## الغرض والنطاق

هذه الوثيقة تخص الدفعة الأولى الآمنة فقط. لا تغيّر الدفعة الحالية مخطط قاعدة البيانات، ولا مسارات `bids.submit` أو رفع الوثائق، ولا تعيد تشفير بيانات قائمة. الهدف هو تثبيت الافتراضات الأمنية وإنشاء مكوّن تشفير قابل للاختبار قبل ربطه بالتخزين.

## الأصول الحساسة

الأصول التي يجب حمايتها هي مبلغ العرض، النص الفني، أي payload منظم مرتبط بالعرض، محتوى وثائق العرض، ومفاتيح التشفير. أما معرف العرض والصفقة وحالة العرض والتواريخ اللازمة للفهرسة والتدقيق فيمكن أن تبقى metadata غير سرية بقدر ما تسمح به سياسة الخصوصية.

## نموذج الخصوم

نفترض خصماً يستطيع قراءة نسخة من قاعدة البيانات أو كائنات التخزين، أو الحصول على رابط تخزين قديم، أو إرسال طلبات API خارج الصلاحية، أو تعديل ciphertext. كما نفترض أخطاء تشغيلية مثل تسريب السجلات أو إعادة المحاولة أو تدوير المفتاح. لا تفترض هذه الدفعة حماية جهاز المستخدم المخترق أو منع مسؤول البنية التحتية من الوصول إلى Secret Manager؛ لذلك يلزم لاحقاً فصل الصلاحيات والمراقبة والتدقيق.

## invariants إلزامية

يجب ألا يكون plaintext للعروض موجوداً في التخزين الدائم بعد الربط النهائي. يجب أن يفشل فك التشفير عند تعديل ciphertext أو nonce أو authentication tag أو associated data. يجب ألا يُسمح بفك محتوى العرض عبر مسار التطبيق قبل تحقق الوقت الخادمي وحالة جلسة الفتح المختومة والنطاق الوظيفي. يجب ألا تظهر المفاتيح أو plaintext في السجلات أو رسائل الأخطاء.

## التصميم المبدئي

سيستخدم كل payload مفتاح بيانات عشوائياً مستقلاً، مع AES-256-GCM وnonce عشوائي بطول 12 بايت وauthentication tag بطول 16 بايت. تُثبت هوية الكيان داخل AAD، مثل `bid:{bidId}:payload:v1`، لمنع نقل ciphertext بين عروض مختلفة. تُخزن نتيجة الدفعة الأولى ككائن typed يحتوي `version`, `algorithm`, `keyVersion`, `nonce`, `ciphertext`, `authTag`، بينما يبقى تغليف مفتاح البيانات بمفتاح رئيسي مخصص خارج نطاق هذه الدفعة حتى يتم توفير Secret Manager production key.

## ما لا تنفذه هذه الدفعة

لا توجد migration، ولا dual-write، ولا تغيير في S3، ولا فك تشفير فعلي لمسارات API، ولا استخدام لمفتاح الإنتاج، ولا حذف للحقول القديمة. لا تعتبر الاختبارات المعزولة دليلاً على اكتمال سرية الإنتاج؛ فهي تثبت فقط صحة primitive وحدود العقد قبل الدمج.

## معايير الانتقال للدفعة التالية

لا نربط الخدمة بمسارات العروض قبل نجاح اختبارات round-trip، رفض المفتاح الخاطئ، كشف العبث، رفض AAD المختلف، وعدم قبول nonce غير صالح، وبعد تحديد اسم السر الإنتاجي وآلية التدوير والاسترجاع والفشل الآمن. يجب أخذ نسخة احتياطية واختبار الاسترجاع قبل أي ترحيل.
