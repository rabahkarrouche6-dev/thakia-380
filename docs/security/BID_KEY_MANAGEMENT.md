# سياسة إدارة مفاتيح تشفير العروض

## المبدأ

يُستخدم مفتاح رئيسي مخصص لتغليف مفاتيح البيانات، ولا يُعاد استخدام `JWT_SECRET` أو أي سر خاص بالمصادقة. لكل payload مفتاح بيانات عشوائي مستقل، وتُخزن نسخة المفتاح المغلفة فقط مع ciphertext وnonce ووسم التوثيق وإصدار المفتاح.

## الإصدارات والتدوير

يُعرّف كل مفتاح رئيسي بإصدار غير قابل للتغيير مثل `bid-master-v1`. عند التدوير، تُستخدم النسخة الجديدة للتشفير، بينما تبقى النسخة السابقة للقراءة وفك البيانات القديمة خلال فترة انتقال محددة. لا يتم حذف النسخة القديمة قبل إعادة تشفير جميع البيانات والتحقق من hash واختبار الاسترجاع.

## التخزين والوصول

يُحفظ المفتاح في Secret Manager أو متغير سرّي محمي، ولا يظهر في قاعدة البيانات أو السجلات أو رسائل الأخطاء. تقتصر عملية فك التشفير على مسار خادمي مصادق ومخوّل وبعد تحقق حالة جلسة الفتح والوقت القانوني. لا تُعاد المفاتيح أو plaintext إلى العميل.

## الاسترجاع والفشل الآمن

يجب أن تكون النسخ الاحتياطية مشفرة وقابلة للاسترجاع في بيئة منفصلة، مع اختبار دوري موثق. عند فقدان المفتاح أو فشل التحقق، يُرفض فك التشفير ويُعاد خطأ عام للمستخدم مع تسجيل حدث أمني غير حساس. لا يجوز استخدام fallback أو مفتاح تجريبي في الإنتاج.

## حالة التنفيذ

هذه السياسة موثقة، لكن تفعيلها الإنتاجي مؤجل لأن `BID_ENCRYPTION_MASTER_KEY` الحالي لم ينجح في اختبار 32 بايت. لذلك لا تُعد سرية العروض أو التدوير أو الاسترجاع منفذة إنتاجياً بعد.
