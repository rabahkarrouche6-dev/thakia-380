# RBAC & AUDIT REMEDIATION PLAN

## نطاق المراجعة

تغطي هذه الخطة أدوار `supplier` و`authority` و`regulator` و`admin` والموارد الحساسة الحالية: الصفقات، العروض، الوثائق، جلسات الفتح، التقييم، الإسناد، التحليلات، سجل التدقيق، وبيانات الملف/المنظمة. لا تغيّر الخطة أسماء الأدوار أو نموذج البيانات إلا عند وجود فجوة مؤكدة تستلزم ذلك.

## الملاحظات المؤكدة من الكود

يوجد تحقق مصادقة مركزي عبر `protectedProcedure`، وتوجد حواجز دورية متفرقة داخل `server/routers.ts`. الفجوة الحرجة المؤكدة هي أن `auth.setRole` يسمح لأي مستخدم مصادق بدور `user` باختيار `supplier` أو `authority` أو `regulator` دون موافقة أو تحقق مؤسسي. هذه ثغرة تصعيد صلاحيات وليست مشكلة واجهة.

توجد أيضاً فجوات تغطية مؤكدة في الاختبارات: لا يوجد إثبات كافٍ للوصول غير المصادق، أو عزل مورد عن عرض مورد آخر عبر المعرف، أو عزل مصلحة متعاقدة عن صفقة مصلحة أخرى، أو منع IDOR في تنزيل الوثائق، أو عزل رؤية سجلات التدقيق على مستوى الأدوار. كما أن `tenders.update` لا يسجل حدث تدقيق رغم كونه تغييراً حساساً. طبقة السياق لا توفر request/correlation ID ولا snapshot لدور الفاعل، لذلك لن تدّعي الخطة وجود هذه الحقول قبل إضافتها فعلياً.

| قراءة عروض صفقة | مرفوض افتراضيًا قبل الفتح | مسموح فقط ضمن جلسة الفتح/التقييم الموثقة | قراءة مراقبة فقط إذا عقدها موجود | حسب الإجراء الإداري الموثق |

| التحليلات | مرفوضة | غير متاحة إلا ما يخدم صفقتها | مسموح للقراءة | مسموح |
| Audit logs | مرفوض | مرفوض افتراضيًا | مسموح للقراءة الرقابية | مسموح |

## خطة الإصلاح الأقل تغييراً

1. إغلاق `auth.setRole` للمستخدم العادي: إبقاء الدور `user` إلى أن يتم تعيين الدور عبر مسار موثوق، مع السماح لـ `admin` فقط بتغيير أدوار المستخدمين إذا كان ذلك مدعوماً فعلياً. لا يتم تغيير أسماء الأدوار.
2. إضافة helper خادمي موحد للتحقق من ملكية الصفقة والعرض والوثيقة قبل كل عملية حساسة، أو تقوية الإجراءات الحالية التي تستخدم معرفات مباشرة.
3. تقييد إجراءات قراءة وتنزيل الوثائق والعروض بعلاقة الكيان والـ workflow، مع اختبار الوصول المباشر للـ API بعيداً عن الواجهة.
4. تسجيل `tenders.update` وأي عملية حساسة ناقصة باستخدام الحقول الحالية الآمنة. إضافة `actorRole` أو `requestId` فقط إذا أضيفت بنية فعلية لها؛ لا يتم تخزين كلمات مرور أو tokens أو محتوى وثائق أو PII غير لازمة.
5. إضافة اختبارات إلزامية للفشل والنجاح، مع اختبار عدم كشف سجل التدقيق لغير الأدوار المخولة.

## الملفات المتوقعة

| الملف | سبب التغيير |
|---|---|
| `server/routers.ts` | إغلاق self-role assignment، تقوية object-level checks، وتسجيل الأحداث الناقصة |
| `server/db.ts` | إضافة استعلامات ملكية أو استعلامات مقيدة عند الحاجة |
| `server/permissions.test.ts` | اختبارات RBAC والوصول غير المصادق وIDOR |
| `server/core-procurement-flow.test.ts` | تغطية العمليات الحساسة المتقاطعة مع التدفق |
| `server/rbac-audit-remediation.test.ts` | اختبار مستقل للحدود الجديدة وسجل التدقيق |
| `drizzle/schema.ts` | لا تغيير متوقع؛ لا يضاف حقل إلا إذا أثبتت البنية حاجته |

## الاختبارات الأمنية المطلوبة

يجب إثبات رفض الوصول غير المصادق، ومنع مورد من قراءة عرض مورد آخر أو وثيقته، ومنع مصلحة من الوصول إلى صفقة غير مملوكة لها، ومنع الوصول المباشر عبر تبديل المعرفات، والتحقق من حدود regulator، وتقييد audit visibility، وإنشاء حدث تدقيق بعد كل عملية حساسة. يجب تشغيل TypeScript والاختبارات والبناء بعد الإصلاح.

## خارج نطاق هذه المرحلة

لا تشمل الخطة تغيير أسماء الأدوار، أو إضافة MFA، أو نظام موافقات مؤسسي كامل، أو تحويل المشروع إلى Django/DRF/Next.js، أو إعادة تصميم الواجهة. هذه العناصر تحتاج قراراً مستقلاً ونماذج بيانات وعقوداً جديدة.
