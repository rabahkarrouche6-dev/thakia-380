# BID OPENING SECURITY & IMPLEMENTATION PLAN

## 1. نطاق المرحلة والحكم المسبق

تقتصر هذه المرحلة على **فتح العروض المغلقة** بعد الإرسال النهائي، ولا تشمل التقييم أو الإرساء أو التوقيع القانوني. البنية الحالية مبنية على React/Vite وtRPC وDrizzle/MySQL، وليست Django/DRF وNext.js كما ورد في الوصف الوظيفي؛ لذلك ستُنفذ العقود داخل البنية الفعلية للمشروع دون إنشاء طبقة موازية.

الوضع الحالي لا يحقق فتحاً آمناً بعد. نموذج `Bid` يملك الحالات `draft` و`submitted` و`under_review` و`accepted` و`rejected` فقط، ولا توجد حالة sealed أو حقل openedAt أو جلسة فتح أو محضر فتح. كما أن `bids.forTender` يعيد كل العروض غير المسودة للمصلحة المتعاقدة، و`bids.documents.download` يسمح للمصلحة المتعاقدة بتنزيل وثائق أي عرض غير مسودة، مما يفتح مسار وصول مباشر قبل الفتح. لا توجد حالياً إجراءات أو واجهة لجلسة الفتح.

> **قاعدة الأمان الأساسية:** لا يكفي إخفاء زر الفتح في الواجهة. يجب أن يرفض الخادم كل قراءة حساسة وكل محاولة فتح قبل الوقت المحدد، وأن يستخدم وقت الخادم المأخوذ داخل الإجراء أو قاعدة البيانات لا ساعة العميل.

## 2. نموذج الحالة الحالي والفجوات

| الكيان | الحالات الحالية | الحالة المطلوبة لهذه المرحلة | الفجوة |
|---|---|---|---|
| Tender | `draft`, `published`, `closed`, `evaluation`, `awarded`, `cancelled` | يبقى دون حالة جديدة؛ جلسة الفتح تكون مرتبطة بصفقة منشورة/مغلقة زمنياً | لا يوجد سجل فتح مستقل |
| Bid | `draft`, `submitted`, `under_review`, `accepted`, `rejected` | `submitted` يعامل كعرض مختوم، أو تضاف `sealed` إن كان تعديل enum مقبولاً؛ بعد الفتح ينتقل إلى `under_review` | لا يوجد `openedAt` ولا إثبات فتح لكل عرض |
| Opening session | غير موجود | سجل واحد لكل صفقة، بمعرف فريد للصفقة، `scheduledAt`, `openedAt`, `openedBy`, `status`, وملخص المحضر | يحتاج جدولاً جديداً وقيود uniqueness |
| Opening minutes | غير موجود | بيانات محضر مرتبطة بجلسة واحدة، قابلة للعرض والتصدير اللاحق | لا يوجد نموذج أو endpoint |
| AuditLog | `actorId`, `action`, `entityType`, `entityId`, `result`, `metadata`, `createdAt` | نفس النموذج مع أحداث ثابتة باللغة الإنجليزية داخل `action` وmetadata JSON آمن | لا توجد حقول request_id مستقلة أو ضمان ذري لكتابة السجل |

## 3. الانتقالات المقترحة والمسموحة

يُعتمد `submitted` كحالة مختومة في أقل تغيير ممكن، مع إضافة `openedAt` لكل عرض. إذا أظهرت مراجعة المخطط أن إضافة enum `sealed` آمنة وغير مربكة للعقود الحالية، يمكن استعمال `sealed` كاسم صريح؛ غير أن الخطة الأساسية لا تضيف حالة جديدة للصفقة ولا تغيّر معنى العرض المرسل.

| الانتقال | الشرط الخادمي | المسموح له |
|---|---|---|
| `draft → submitted` | الصفقة `published`، الأجل لم ينتهِ، الملكية صحيحة، الحقول الإلزامية مكتملة | supplier أو admin ضمن عقد الإرسال الحالي |
| `submitted → under_review` | جلسة فتح ناجحة، وقت الخادم ≥ وقت الفتح، العرض تابع للصفقة وغير مفتوح سابقاً | إجراء فتح داخلي محمي، وليس endpoint عاماً لتعديل الحالة |
| `submitted → submitted` | قراءة قبل الفتح لا تعرض payload أو وثائقاً حساسة | لا ينطبق كتحويل حالة |
| `under_review → accepted/rejected` | مرحلة التقييم الحالية تبدأ بعد الفتح | authority المالك أو admin وفق العقود الحالية |
| جلسة `scheduled → opened` | وقت الخادم يسمح، الصفقة في حالة `published` أو `closed` وفق معيار الإغلاق المعتمد، وعدم وجود جلسة مفتوحة سابقاً | authority المالك وadmin فقط في MVP؛ regulator قراءة وتدقيق فقط ما لم تعتمد الجهة غير ذلك |

لا يجوز لأي endpoint قراءة `amount` أو `proposal` أو وثائق العرض للمصلحة المتعاقدة قبل نجاح جلسة الفتح. كما لا يجوز تحديث العرض أو وثائقه بعد الإرسال النهائي، وتبقى الصفوف محفوظة دون حذف.

## 4. فرض وقت الخادم

يجب أن يقرأ endpoint الأهلية والـ mutation وقتاً من الخادم عند كل طلب، وأن يقارن ذلك بموعد الفتح المحفوظ في قاعدة البيانات. لا يعتمد القرار على `Date.now()` في العميل، ولا تُقبل قيمة زمنية مرسلة من الواجهة كمرجع. يمكن استخدام `new Date()` داخل الخادم لأن معيار القرار هو وقت تنفيذ الخادم، مع تفضيل وقت قاعدة البيانات في الاستعلام أو transaction عند توفره.

موعد الفتح المقترح في MVP هو `tender.deadline` نفسه إذا لم توجد خانة مستقلة في النموذج الحالي. يجب توثيق ذلك صراحة في الواجهة والمحضر. إذا كان التشغيل القانوني يميز بين نهاية الاستقبال وموعد الفتح، فهذه فجوة نموذجية تستلزم إضافة `openingAt` مستقل إلى `tenders` قبل الإنتاج؛ لا يجوز اشتقاق موعد قانوني مختلف من الواجهة.

## 5. الصلاحيات

| العملية | supplier | authority المالك | regulator | admin |
|---|---:|---:|---:|---:|
| معرفة أهلية الفتح لصفقة مملوكة | لا | نعم | قراءة حالة فقط، دون فتح | نعم |
| محاولة فتح العروض | لا | نعم | لا في MVP الحالي | نعم |
| قراءة metadata الآمنة قبل الفتح | لا | نعم بالحد الأدنى | نعم حسب نطاق التدقيق | نعم |
| قراءة payload ووثائق العرض قبل الفتح | لا | لا | لا | لا، إلا إذا اعتُمد كاستثناء تشغيلي صريح | 
| قراءة payload ووثائق العرض بعد الفتح | لا | نعم للصفقة المملوكة | نعم للتدقيق | نعم |
| عرض محضر الفتح بعد إنشائه | لا | نعم للصفقة المملوكة | نعم | نعم |

اختيار `authority` المالك و`admin` للفتح هو أقل امتداد متوافق مع roleProcedure الحالية، لكنه يحتاج اعتماداً قانونياً/تشغيلياً لأن النظام لا يملك حالياً دوراً مستقلاً للجنة فتح. لا يجوز توسيع صلاحية regulator إلى mutation لمجرد وجوده في النظام.

## 6. تصميم الـ endpoints

| العقد المقترح | النوع | الوظيفة | القيود الأساسية |
|---|---|---|---|
| `bids.openingEligibility` | protected query | يعيد حالة آمنة: `before_opening`, `available`, `opened`, `no_submitted_bids`, `permission_denied` أو `server_failure` | لا يعيد payload أو وثائقاً؛ يتحقق من الملكية والدور ووقت الخادم |
| `bids.openingSession` | protected query | يعيد جلسة الفتح ومحضرها عند وجودها، وmetadata قبل الفتح | لا يعرض التفاصيل الحساسة قبل `openedAt` |
| `bids.open` | role-protected mutation | ينفذ الفتح لمرة واحدة ويعيد المحضر | transaction، قفل/unique tenderId، تحقق الوقت والصفقة والملكية، تحديث كل عرض مؤهل، audit |
| `bids.openingMinutes` | protected query | يعرض المحضر بعد الفتح | authorization على tender وsession |
| `bids.forTender` | role-protected query | يعدّل projection الحالية لتعيد metadata فقط قبل الفتح، والـ payload بعد الفتح | لا تعتمد على filter في العميل |
| `bids.documents.download` | protected query | يمنع رابط S3 الموقّع قبل الفتح | فحص حالة bid/session قبل إصدار الرابط |

يجب أن تتضمن استجابة الأهلية وقت الخادم الحالي بصيغة عرض، والموعد المحفوظ، وسبب الحالة باللغة العربية، من دون كشف بيانات العرض. الأخطاء الخادمية تستخدم `TRPCError` بعقود واضحة، مع تسجيل محاولة الفتح المرفوضة حتى عند عدم وجود صلاحية أو عدم تحقق الموعد.

## 7. حماية التكرار وIdempotency

يجب إنشاء جدول `bidOpeningSessions` بحيث يكون `tenderId` فريداً، مع status وopenedAt وopenedBy وminutes metadata. ينفذ `bids.open` transaction واحدة: يتحقق من عدم وجود جلسة مفتوحة، يقفل/يعيد قراءة الصف، ينشئ الجلسة، يحدّث العروض المؤهلة إلى `under_review` ويضع `openedAt`، ثم ينشئ سجل audit ومحضر الفتح. إذا وصلت محاولة ثانية بعد نجاح الأولى، تعيد حالة `opened` والمحضر الموجود أو ترفض بوضوح؛ لا تعيد تحديث العروض ولا تنشئ محضراً ثانياً.

لا يكفي فحص application-level فقط عند التوازي. يجب أن يسانده unique constraint على `tenderId`، ومعاملة قاعدة بيانات أو آلية قفل متاحة في Drizzle/MySQL. إذا تعذر ضمان transaction حقيقية في البيئة الحالية، يجب تصنيف الفتح كغير جاهز للإنتاج وعدم الادعاء بأن منع السباق مكتمل.

## 8. شكل محضر الفتح

يقترح حفظ محضر منظم مرتبطاً بجلسة الفتح، مع إبقاءه مبنياً على البيانات الحقيقية فقط:

| الحقل | المصدر |
|---|---|
| `tenderId` و`reference` | Tender الفعلي |
| `title` | Tender الفعلي |
| `serverOpenedAt` | وقت الخادم عند نجاح العملية |
| `scheduledOpeningAt` | `tender.deadline` حالياً، أو `tender.openingAt` إذا أضيف لاحقاً |
| `submittedCount` | عدد العروض ذات `submitted` قبل العملية |
| `openedBids` | معرف العرض، supplierId أو اسم مؤسسي إن كان مسموحاً، submittedAt، amount/proposal بعد الفتح فقط |
| `openedBy` | مستخدم العملية، وفق سياسة عرض الهوية |
| `exceptions` | أخطاء أو عروض لم تُفتح مع سبب فعلي |
| `auditEventIds` | معرفات سجلات التدقيق إن أضيفت إلى العقد |

المحضر ليس توقيعاً إلكترونياً ولا شهادة قانونية ولا دليلاً على عدم العبث ما لم تضف المنصة آلية توقيع/ختم فعلياً. في هذه المرحلة يكون قابلاً للعرض، ويُحفظ server-side، ويُترك التصدير إلى مرحلة لاحقة أو ينفذ كتنزيل read-only دون ادعاء قيمة قانونية.

## 9. أحداث Audit المطلوبة

يجب استخدام مفاتيح ثابتة قابلة للبحث، مع metadata JSON خالٍ من payload السري قبل الفتح:

| الحدث | متى يسجل | النتيجة |
|---|---|---|
| `bid_submitted` | عند إرسال العرض النهائي | `success` أو `failure` |
| `bid_opening_attempted` | عند كل محاولة endpoint فتح | `success` أو `failure` |
| `bid_opened` | لكل عرض انتقل فعلياً إلى حالة مفتوحة/قيد التقييم | `success` |
| `bid_opening_denied` | قبل الموعد أو عند رفض الدور/الملكية/الحالة | `denied` |
| `opening_minutes_generated` | بعد حفظ المحضر بنجاح | `success` |

الفجوة الحالية أن `auditLogs` لا يحتوي request_id مستقلاً، وأن `logAudit` لا يضمن فشل العملية عند تعذر قاعدة البيانات. لذلك ينبغي إضافة requestId إلى metadata على الأقل، مع عدم تخزين `proposal` أو بيانات وثائق حساسة في السجل.

## 11. الاختبارات الأمنية المطلوبة

يجب أن تثبت الاختبارات أن supplier لا يستطيع استدعاء eligibility أو open أو قراءة `forTender` الخاص بالسلطة، وأن authority غير المالكة ترفض، وأن regulator لا يستطيع تنفيذ mutation، وأن admin يخضع لنطاق صريح لا لتجاوز صامت. يجب اختبار الوصول المباشر للـ API قبل الموعد، وبعد الموعد، وبعد نجاح الفتح، مع التحقق من عدم وجود payload أو رابط وثيقة في الاستجابة السابقة للفتح.

كما يجب اختبار أن محاولة فتح ثانية لا تنشئ جلسة أو محضراً إضافياً، وأن محاولات متزامنة لا تفتح الصفقة مرتين، وأن حالة `no submitted bids` تنتج محضراً حقيقياً بعدد صفر دون نجاح مضلل. يجب اختبار فشل قاعدة البيانات أو التخزين، وفشل سجل التدقيق، وحالات loading/empty/error/success في الواجهة، ثم التحقق بصرياً من RTL والموبايل.

## 12. تعارضات يجب اعتمادها قبل التنفيذ

يوجد تعارض جوهري بين الوصف القانوني الذي يفترض موعد فتح مستقل وبين النموذج الحالي الذي يملك `deadline` فقط. الخطة لا تخترع موعداً مستقلاً؛ تستخدم `deadline` مؤقتاً وتوصي بإضافة `openingAt` قبل Pilot قانوني إذا كان موعد الفتح منفصلاً.

كما لا يوجد دور `opening_committee` أو آلية quorum أو توقيع إلكتروني. لذلك لا ينبغي تقديم التنفيذ على أنه فتح لجنة قانونية مكتملة. سيقتصر MVP على المستخدمين الموجودين والمصرح لهم صراحة، مع إبقاء regulator في وضع القراءة والتدقيق إلى أن تعتمد الجهة سياسة الصلاحيات.

## 13. قرار بدء التنفيذ

يمكن بدء التنفيذ التقني بأقل تغيير آمن بعد اعتماد نقطتين: اعتماد `tender.deadline` كموعد الفتح المؤقت، واعتماد `authority` المالك و`admin` كمنفذين للفتح في MVP. إذا لم يُعتمد أي منهما، يجب تعديل الخطة وإضافة حقول/دور رسميين قبل لمس الكود.

هذا المستند خطة تنفيذ فقط؛ لم تُنفذ بعد جداول أو endpoints أو واجهة فتح العروض.
