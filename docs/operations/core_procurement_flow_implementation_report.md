# CORE PROCUREMENT FLOW IMPLEMENTATION REPORT

## الحكم التنفيذي

تم إغلاق الجزء الأساسي من مسار الصفقة والعرض اعتماداً على البيانات الحقيقية وعقود الخادم الحالية، مع إضافة دعم وثائق المجال ومسودة العرض. أصبحت العمليات الحساسة محكومة خادمياً، بما في ذلك الملكية، الدور، حالة الكيان، وأجل استقبال العروض باستخدام وقت الخادم. لا يزال المسار غير مؤهل باعتباره دورة مشتريات عمومية مكتملة قانونياً، لأن فتح العروض ومحضر الفتح والعرض المختوم والتقييم متعدد المراحل ليست ضمن البنية الحالية.

## ما تم تنفيذه

| المجال | التنفيذ الفعلي |
|---|---|
| إنشاء الصفقة | إنشاء صفقة بحالة `draft` مع الحقول الفعلية الحالية: العنوان، الوصف، التصنيف، الموقع، الميزانية، العملة، والموعد النهائي. |
| التحقق | تحقق واجهي قبل الحفظ والنشر، مع تحقق خادمي مستقل لعقود الإنشاء والتحديث والنشر. |
| وثائق الصفقة | إضافة رفع وثائق حقيقية إلى التخزين S3 وحفظ metadata في قاعدة البيانات قبل النشر، مع قائمة وتنزيل محمي للوثائق المسموح بها. |
| المسودة والنشر | حفظ أولي عبر `tenders.create`، والحفظ اللاحق عبر `tenders.update`، والنشر عبر `tenders.publish` بعد تحقق الملكية والحالة. |
| الصفقات المنشورة | المورد يقرأ الصفقات المنشورة عبر `tenders.published` فقط، مع البحث والتصفية والفرز محلياً على الحقول الحقيقية. |
| تفاصيل الصفقة | عرض بيانات الصفقة والميزانية والموعد النهائي، وإتاحة وثائق الصفقة من خلال رابط موقّع صادر من الخادم. |
| مسودة العرض | إنشاء مسودة عبر `bids.createDraft`، وتحديثها عبر `bids.updateDraft`، مع رفع وثائق العرض قبل الإرسال النهائي. |
| الإرسال النهائي | إرسال العرض عبر `bids.submit` مع فحص القيمة والملخص الفني والملكية والصفقة والأجل. |
| انتهاء الأجل | استعلام الصفقات المنشورة يستبعد المنتهية، كما يرفض الخادم إنشاء أو تعديل أو إرسال العرض بعد `deadline` باستخدام `Date.now()` على الخادم. |
| السجل التدقيقي | تسجيل إنشاء المسودة، حفظها، رفع وثائق الصفقة والعرض، تنزيل الوثائق، وإرسال العرض النهائي في `AuditLog`. |
| الرسائل والحالات | إضافة حالات loading وempty وerror وsuccess وحالة انتهاء الأجل برسائل عربية واضحة في واجهتي authority وsupplier. |

## الملفات التي تغيرت

### ملفات التطبيق

- `drizzle/schema.ts`: إضافة حالة `draft` لمسار العرض وجداول metadata لوثائق الصفقات والعروض.
- `drizzle/0002_wise_peter_parker.sql`: migration غير هدّامة مطبقة على قاعدة البيانات.
- `server/db.ts`: إضافة helpers لإنشاء وسرد واسترجاع metadata الوثائق، مع استعلامات المسودات والملكية.
- `server/routers.ts`: إضافة عقود الوثائق ومسودة العرض والتنزيل المحمي والإرسال النهائي وفحص وقت الخادم وسجل التدقيق.
- `client/src/pages/AuthorityTenderCreate.tsx`: ربط رفع الوثائق بحفظ المسودة والنشر وحالات النجاح والفشل.
- `client/src/pages/SupplierWorkspace.tsx`: إضافة وثائق الصفقة المتاحة، وتنزيلها، ومسودة العرض، ووثائق العرض، والإرسال النهائي وحالة الموعد المنتهي.

### ملفات الاختبار والتوثيق

- `server/supplier-workspace.view.test.ts`: تحديث عقد واجهة المورد لمسار المسودة والوثائق.
- `server/core-procurement-flow.test.ts`: اختبار عقدي للمخطط والخادم والواجهتين.

## migrations

تم توليد وتطبيق migration `drizzle/0002_wise_peter_parker.sql`. التغيير غير هدّام: أضيفت جداول metadata للوثائق، وتم توسيع حالات العرض لدعم المسودة. لا يتم تخزين bytes داخل قاعدة البيانات؛ التخزين يتم عبر S3 وتُحفظ المفاتيح والmetadata فقط.

## state transition matrix

### Tender

| الانتقال | الحالة |
|---|---|
| `draft → published` | مدعوم عبر `tenders.publish` بعد الملكية والتحقق. |
| `published → closed` | مدعوم عبر `tenders.close`. |
| `closed → evaluation` | مدعوم عبر `tenders.startEvaluation`. |
| `evaluation → awarded` | مدعوم عبر قرار الإسناد بعد قبول عرض. |
| `evaluation → cancelled` | مدعوم عبر قرار الإلغاء. |
| `published → cancelled` أو تعديل جوهري بعد النشر | غير مدعوم كمسار منضبط في هذا النطاق. |

### Bid

| الانتقال | الحالة |
|---|---|
| لا يوجد عرض → `draft` | مدعوم عبر `bids.createDraft` قبل الموعد. |
| `draft → draft` | مدعوم عبر `bids.updateDraft` قبل الموعد وبواسطة المالك. |
| `draft → submitted` | مدعوم عبر `bids.submit` قبل الموعد. |
| `submitted → under_review/accepted/rejected` | مدعوم عبر `bids.evaluate` وفق صفقة قيد التقييم. |
| `submitted → sealed/opened` | غير مدعوم حالياً. |
| حذف العرض أو استبداله عند الانتقال | غير منفذ؛ التحديث يتم على السجل نفسه ولا يحذف بيانات العرض. |

## الاختبارات المنفذة ونتائجها

- TypeScript: **نجح** عبر `pnpm exec tsc --noEmit`.
- Vitest: **نجح**؛ 11 ملف اختبار و39 اختباراً.
- اختبارات الصلاحيات: **نجحت ضمن المجموعة**، بما في ذلك عزل أدوار authority وregulator وحماية الملكية.
- اختبار الموعد النهائي: **نجح**؛ رفض الإرسال بعد انتهاء الأجل مثبت خادمياً.
- اختبار عقود Core Procurement Flow: **نجح** عبر `server/core-procurement-flow.test.ts`.
- Build: **نجح** عبر `pnpm build`، مع تحذير حجم بعض حزم JavaScript فقط.
- RTL وMobile: تم التقاط والتحقق بصرياً من `/app` على سطح المكتب والهاتف. تعذر إثبات جلسة supplier فعلية من اللقطة الحالية لأن جلسة المعاينة المتصلة تخص authority؛ لذلك لا تعتبر اللقطات وحدها اختبار E2E للمورد.
- lint: **فشل** لأن Prettier يرصد مشكلات تنسيق قائمة في 75 ملفاً، منها ملفات قديمة وملفات التعديل الحالي. لم تُنفذ إعادة تنسيق شاملة حتى لا تختلط تغييرات الشكل مع منطق المشتريات.

## النواقص المتبقية

- لا يوجد نموذج مستقل لشروط الأهلية أو معايير التقييم أو الضمانات، عمداً خارج النطاق الحالي.
- لا يوجد فتح عروض قانوني بوقت خادم مستقل ولا `sealed/opened` في Bid.
- لا يوجد محضر فتح عروض قابل للتدقيق.
- لا يوجد تدفق إصدار جديد لتعديل صفقة منشورة؛ التعديل الجوهري بعد النشر غير مدعوم.
- لا توجد حماية تنقيح/إخفاء محتوى وثائق العرض على مستوى تصنيف الوثيقة؛ الصلاحية الحالية تعتمد على المالك والدور وحالة العرض.
- لا يوجد اختبار E2E كامل عبر حسابات حقيقية أو متصفح مصادق عليه لمسار authority ثم supplier.
- لا يوجد تحقق من نوع الملف ومحتواه عبر فحص أمني عميق؛ التحقق الحالي يعتمد على metadata والحدود الموجودة في العقد.
- لا يوجد تكامل Django/DRF أو Next.js في هذا المستودع؛ البنية الفعلية React/Vite وExpress/tRPC وDrizzle/MySQL.

## مخاطر Pilot

| الخطر | الأثر | الإجراء المقترح |
|---|---|---|
| غياب فتح العروض ومحضر الفتح | لا يمكن اعتبار الدورة متوافقة مع دورة فتح رسمية أو غير قابلة للتلاعب زمنياً | بناء عقد خادمي مستقل للفتح وسجل أحداث غير قابل للالتباس قبل Pilot مراقب. |
| صلاحيات الأدوار الإدارية الحالية | قد تسمح بعض العقود بدور admin الواسع، كما أن تعيين الأدوار يحتاج إغلاقاً مستقلاً | منع self-role assignment وربط الترقية بمسار إداري موثق واختبارات رفض. |
| حماية وثائق العرض | رابط S3 الموقّع محمي بالوصول، لكن تصنيف سرية الوثيقة ليس نموذجاً مستقلاً | إضافة سياسة تصنيف ووصول ومراجعة أمنية قبل وثائق حساسة. |
| غياب E2E الإنتاجية | اختبارات Vitest تثبت العقود، لكنها لا تثبت دورة متصفح وملفات كاملة في بيئة تشغيلية | إضافة E2E بحسابات اختبار منفصلة، مع التحقق من الأجل والمنع والـ audit. |
| lint غير أخضر | لا يمنع التشغيل مباشرة، لكنه يقلل جودة بوابة CI ويصعّب المراجعة | معالجة التنسيق على دفعات قبل اعتماد CI إلزامي. |

## الخلاصة

التنفيذ الحالي يغطي مسار MVP عملياً من إنشاء المسودة والنشر إلى عرض المورد ومسودة العرض ورفع الوثائق والإرسال النهائي، مع إنفاذ server-side للملكية والموعد. لكنه لا يغطي بعد دورة المشتريات الكاملة ذات المتطلبات النظامية لفتح العروض ومحضر الفتح والتقييم الرسمي. لذلك التوصية هي **Pilot داخلي محدود ومراقب فقط** بعد اختبار E2E وإغلاق تعيين الأدوار، وليس إطلاقاً عاماً أو اعتماداً قانونياً.
