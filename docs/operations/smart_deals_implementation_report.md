# SMART DEALS IMPLEMENTATION REPORT

## Scope implemented

تم تنفيذ نواة MVP لمنصة **صفقات ذكية** كمنصة عربية RTL لإدارة جزء أساسي من دورة الصفقات العمومية، بدءاً من إنشاء الصفقة ونشرها، مروراً بعرض الصفقات وتقديم العروض وتقييمها، وصولاً إلى قرار الإسناد أو الإلغاء، مع بوابات منفصلة للمصلحة المتعاقدة والمتعامل الاقتصادي والرقابة. كما شملت الأعمال صفحة هبوط عامة، صفحة دخول موحدة، مساحات عمل حسب الدور، سجل تدقيق، ومساعداً إرشادياً لا ينفذ قرارات تعاقدية.

النطاق المنفذ يثبت وجود **نواة workflow قابلة للعرض والاختبار الداخلي**، ولا يثبت جاهزية إطلاق تجريبي مضبوط لمنصة مشتريات عمومية قبل إغلاق الضوابط الزمنية والملفية ومخاطر RBAC المحددة في تدقيق MVP.

## Database changes

تتضمن قاعدة البيانات الحالية الجداول والنماذج التالية: `users` مع الأدوار `user` و`admin` و`supplier` و`authority` و`regulator`؛ `profiles` لبيانات الملف؛ `tenders` للصفقات؛ `bids` للعروض؛ `awardDecisions` لقرارات الإسناد أو الإلغاء؛ `auditLogs` للتدقيق؛ و`assistantMessages` لسجل المساعد الإرشادي.

## API changes

توجد إجراءات tRPC محمية حسب الدور والملكية، من أهمها إجراءات الملف الشخصي، إنشاء الصفقة وتحديثها ونشرها وإغلاقها وبدء التقييم، الصفقات المنشورة، تقديم العرض، عروض المصلحة المتعاقدة، تقييم العرض، قرار الإسناد أو الإلغاء، إجراءات regulator الخاصة بالنظرة العامة والإحصائيات والصفقات وسجل التدقيق، وإجراء المساعد الإرشادي.

تعتمد الواجهة على tRPC مباشرة، ولا تستخدم واجهات REST موازية. الحماية الأساسية مطبقة في الخادم عبر إجراءات الدور والملكية، مع وجود تحقق واجهي مكمل لا يُعد بديلاً عن تحقق الخادم.

## Permissions

يتم تطبيق عزل الأدوار على الخادم. يسمح دور `authority` بإدارة صفقاته وفق ملكية `authorityId`، ويسمح دور `supplier` بالوصول إلى ملفه وعروضه وتقديم العروض ضمن العقود المتاحة، بينما يملك `regulator` صلاحيات قراءة ومراقبة وتحليل وسجل تدقيق دون إجراءات تعاقدية طفرية. يملك `admin` صلاحيات النظام وفق الإجراءات الحالية.

أثبتت اختبارات الصلاحيات الحالية رفض وصول المورد إلى إنشاء صفقات المصلحة المتعاقدة، ورفض وصول regulator إلى تقديم عروض الموردين، ومنع المورد من قراءة عروض المصلحة المتعاقدة، وحماية `regulator.overview`، ومنع regulator من الإجراءات التعاقدية الطفرية.

مع ذلك، يظل **تعيين الدور الأولي** نقطة P0 تحتاج إلى إغلاق صريح؛ فالواجهة لا يمكن أن تكون الضابط الوحيد لتحديد الدور، ويجب أن يكون الإسناد أو الترقية محكوماً بمسار إداري موثق ومراجع.

## State transitions

الحالات الفعلية في schema هي:

| الكيان | الحالات المدعومة فعلياً |
|---|---|
| Tender | `draft` → `published` → `closed` → `evaluation` → `awarded` أو `cancelled` |
| Bid | `submitted` → `under_review` → `accepted` أو `rejected` |
| Contract | لا يوجد نموذج أو انتقالات فعلية في schema الحالية |

توجد إجراءات خادمية لإنشاء الصفقة ونشرها وإغلاقها وبدء التقييم، وتقييم العروض، ثم إسناد الصفقة أو إلغائها. لا ينبغي عرض حالات `SEALED` أو `OPENED` أو `SIGNED` أو `ACTIVE` أو `COMPLETED` أو غيرها باعتبارها حالات مطبقة، لأنها ليست جزءاً من نموذج البيانات الحالي.

## Audit events

يُسجل الخادم أحداثاً ناجحة للعمليات الحساسة عبر `auditLogs`، وتشمل تحديث الملف، إنشاء الصفقة، نشر الصفقة، إغلاق الصفقة، بدء تقييم العروض، تقديم العرض، تقييم العرض، وإسناد الصفقة أو إلغائها. يتضمن السجل الحالي `actorId` و`action` و`entityType` و`entityId` و`result` و`metadata` و`createdAt`.

هذا يغطي أساساً مهماً من التدقيق، لكنه لا يثبت اكتمال الحقول المرجعية المطلوبة مثل `actor_role` و`request_id` و`safe_metadata` المنفصلة، ولا يضمن تسجيل جميع المحاولات الفاشلة أو العمليات الأمنية والتشغيلية خارج هذه الإجراءات.

## Known limitations

المنصة لا تزال تعتمد على Manus OAuth ولا تحتوي نظام كلمات مرور محلياً. لا توجد إدارة مستندات أو رفع ملفات مرتبط بالعروض، ولا حماية S3 أو صلاحيات تنزيل يمكن إثباتها من النموذج الحالي. لا توجد إشعارات حقيقية للآجال أو النشر أو التقييم أو الإسناد.

التحقق الزمني لتقديم العروض وإغلاق الاستقبال وفتح العروض ليس مكتملاً بما يكفي لاعتباره ضابطاً قانونياً مستقلاً. كما لا يوجد نموذج عقد تنفيذي أو متابعة تنفيذ أو محضر فتح عروض كامل أو تحليلات زمنية ومؤشرات مخاطر معتمدة.

## Not implemented

لم تُنفذ إدارة العقود والتنفيذ والمتابعة، رفع الوثائق وحمايتها، محضر فتح العروض، الفتح القانوني بعد الموعد، تقييم متعدد المعايير، الإشعارات، نظام استعادة كلمة مرور محلي، MFA، OCR، التكامل مع موفرات هوية خارجية، E2E كامل لدورة الشراء، نظام مراقبة وتشغيل structured، أو خطة backup/rollback مثبتة في بيئة production-like.

كما لم تُضف حالات قاعدة بيانات غير موجودة، ولم تُنشأ بيانات تجريبية أو مراجعات أو تقييمات وهمية.

## Security risks

| الخطر | الدرجة | الأثر |
|---|---|---|
| إمكانية تعيين أو ترقية الدور دون مسار إداري مغلق ومراجع | P0 | قد يؤدي إلى تجاوز RBAC والوصول إلى بوابة غير مصرح بها. |
| عدم فرض deadline لتقديم العرض على الخادم بشكل مستقل ومثبت اختبارياً | P0 | قد يسمح بتقديم أو تعديل عرض بعد انتهاء الأجل القانوني. |
| غياب حماية ملفات فعلية لأن نموذج الوثائق والرفع غير مكتمل | P0/P1 حسب السيناريو | لا يمكن إثبات سرية الوثائق أو سلامة تنزيلها. |
| عدم وجود محضر فتح عروض وضابط فتح بعد الموعد | P0 | لا يمكن إثبات نزاهة مرحلة الفتح. |
| سجل التدقيق لا يغطي كل المحاولات الفاشلة والحقول المرجعية القياسية | P1 | يضعف التحقيق والمساءلة التشغيلية. |
| عدم وجود structured logging وerror tracking وhealth checks مكتملة | P1 | يؤخر اكتشاف الأعطال ويضعف المراقبة. |
| مشكلات التنسيق وغياب lint أخضر | P1 هندسي | يزيد مخاطر الصيانة والتباين ولا يمثل وحده ثغرة صلاحيات. |

## Recommended next step

الخطوة الأولى الموصى بها هي إغلاق مانعي P0 عبر منع self-role-assignment بقرار خادمي صريح، ثم إضافة تحقق deadline ذري داخل إجراء تقديم العرض مع اختبارات حدود زمنية تشمل المنطقة الزمنية والتزامن.

بعد ذلك ينبغي تنفيذ مرحلة **Auth & Onboarding** بمسار اعتماد أدوار إداري، ثم بناء E2E حقيقي لدورة: إنشاء الصفقة، نشرها، تقديم العرض قبل الأجل، رفض التقديم بعد الأجل، الإغلاق، التقييم، والإسناد، مع سجلات تدقيق قابلة للمراجعة.

وأخيراً ينبغي فصل معالجة التنسيق والـlint في تغيير مستقل، ثم إضافة نموذج الوثائق والتخزين المحمي ومحضر فتح العروض قبل التفكير في Pilot تشغيلي مضبوط.
