# CENTRAL ANALYTICS — PHASE 2 REPORT

**المرحلة:** PHASE 2 — Information Architecture + Metric Design  
**النطاق:** تصميم بنية المعلومات، جرد المقاييس، تعريف قاموس KPI، واختيار Overview MVP لبوابة الإدارة المركزية.  
**القيود:** لا تنفيذ UI، لا إضافة queries، لا تعديل schema، لا charts، ولا تغيير للصلاحيات.  
**المرجع:** تقرير `central_analytics_discovery.md` وملفات المشروع الفعلية.

> **قرار المرحلة:** يمكن اعتماد Overview رقابية وصفية محدودة من البيانات الحالية، بينما تبقى الاتجاهات الزمنية وBid Flow المفصل والتنبيهات ومؤشرات المخاطر خارج MVP إلى أن تعتمد لها queries وتعريفات واختبارات مستقلة.

## 1. Information Architecture

### 1.1 الهدف التشغيلي

يجب أن تمكّن البوابة الإدارة المركزية خلال أقل من دقيقة من فهم وضع المنصة الحالي، وتحديد موضع يحتاج إلى مراجعة، والانتقال إلى سجل أو كيان قابل للفحص، مع بقاء كل العرض **قراءة ومراجعة فقط**. لا تهدف هذه البوابة إلى اتخاذ قرار تعاقدي أو تنفيذ دورة صفقة نيابة عن المصلحة المتعاقدة.

### 1.2 البنية المقترحة

| القسم | الغرض | الحالة في PHASE 2 | مصدر البيانات المطلوب |
|---|---|---|---|
| **Overview** | لقطة موحدة للوضع الحالي مع مؤشرات محدودة وتوزيع حالات وآخر نشاط | **MVP معتمد للتخطيط** | `regulator.stats`, `regulator.tenders`, `regulator.audit` الحالية |
| **Trends** | عرض التغير حسب فترة زمنية للصفقات والعروض والنشاط | مؤجل | queries grouped by date وperiod comparison غير موجودة |
| **Tender Health** | فحص توزيع الصفقات حسب الحالة والفئة والموقع، دون تسمية المخاطر | جزئي؛ يدرج داخل Overview أولاً | `regulator.tenders` الحالية، ثم query تجميعية لاحقة |
| **Bid Flow** | فهم حجم العروض وتوزيع حالات العرض بالنسبة للصفقات | مؤجل | لا توجد query regulator للعروض المجمعة |
| **Audit & Activity** | قراءة النشاط الموثق والبحث في الأحداث | نسخة أولية ضمن Overview؛ شاشة مستقلة لاحقاً | `regulator.audit` الحالية، ثم query بفلاتر |
| **Future-ready** | توضيح ما لم يعتمد بعد مثل المخاطر والتنبيهات والتقارير | بنية توضيحية فقط | لا بيانات تشغيلية في هذه المرحلة |

### 1.3 التنقل والمسارات المتوافقة

لا يضيف هذا المخطط دوراً جديداً ولا يستبدل `/app`. يبقى `/app` نقطة الدخول، ويُستخدم سياق regulator الحالي لتحديد المساحة. عند التنفيذ يمكن تمثيل الأقسام بواسطة query parameter أو routes داخلية متوافقة، مثل:

| العرض المقترح | المسار المتوافق | ملاحظة تنفيذية لاحقة |
|---|---|---|
| Overview | `/app?portal=regulator&view=overview` | العرض الافتراضي |
| Trends | `/app?portal=regulator&view=trends` | لا يُفعل قبل اعتماد query زمنية |
| Tender Health | `/app?portal=regulator&view=tender-health` | يبدأ كتفصيل وصفي للحالات |
| Bid Flow | `/app?portal=regulator&view=bid-flow` | لا يُفعل قبل مصدر bids مجمع |
| Audit & Activity | `/app?portal=regulator&view=audit` | يمكن لاحقاً توسيعه من آخر 50 سجلاً إلى فلاتر خادمية |

هذه المسارات هي اقتراح IA فقط، وليست طلباً لتنفيذ routing أو واجهة في هذه المرحلة.

### 1.5 Permission map

تظل الإدارة المركزية ضمن الدور `regulator`. كل query مستقبلية يجب أن تستخدم الحارس الخادمي نفسه `roleProcedure(["regulator", "admin"])` أو حارساً أكثر تقييداً. لا يسمح أي قسم من IA بالإنشاء أو النشر أو الإغلاق أو التقييم أو الإسناد أو الإلغاء.

| القدرة | regulator | authority | supplier | مبدأ الحماية |
|---|---:|---:|---:|---|
| قراءة Overview المركزية | نعم | لا عبر إجراءات regulator | لا عبر إجراءات regulator | server-side role guard |
| قراءة قائمة الصفقات المركزية | نعم | لا عبر هذا المسار | لا عبر هذا المسار | server-side role guard |
| قراءة سجل النشاط | نعم | لا عبر هذا المسار | لا عبر هذا المسار | server-side role guard |
| تعديل أو نشر صفقة | لا | نعم وفق الملكية | لا | مرفوض خادمياً |
| تقييم عرض أو اتخاذ قرار | لا | نعم وفق الملكية | لا | مرفوض خادمياً |
| drill-down تحليلي مستقبلي | نعم للقراءة فقط | حسب الإجراء المنفصل | حسب الإجراء المنفصل | لا يعاد استخدامه كصلاحية mutation |

| المعرّف | المقياس | نوعه | المصدر الحالي | الجاهزية | الغرض |
|---|---|---|---|---|---|

| `M-TND-003` | الصفقات المسندة | filtered count | `regulator.stats.awarded` محسوب خادمياً | متاح خادمياً، غير مستعمل في UI | وصف مخرجات الإسناد دون نسبة أو اتجاه |

### 2.1 قواعد اعتماد المقياس

لا يدخل المقياس إلى Overview إلا إذا كان له مصدر محدد، وصيغة حساب ثابتة، ونطاق زمني واضح إن كان زمنياً، وحالة empty وerror، وتفسير لا يخلط بين الوصف والحكم. وجود حقل في schema وحده لا يكفي لاعتماد مقياس واجهة.

### 3.1 مؤشرات ممنوعة في Overview MVP

لا تعتمد Overview أي مؤشر باسم «درجة المخاطر»، أو «معدل التنافس»، أو «الموردون النشطون»، أو «التأخر»، أو «مؤشر النزاهة»، أو «النمو»، أو «التنبؤ». هذه التسميات تتطلب تعريفات ومصادر وفترات وقواعد غير موجودة في المشروع.

## 4. Overview MVP Selection

### 4.1 الاختيار النهائي

يُقترح أن تتكون Overview MVP من **خمسة مؤشرات رئيسية فقط**، مع وحدة وصفية للحالات ووحدة نشاط محدودة. هذا يحافظ على الهرمية ويمنع تحويل الشاشة إلى تقرير شامل غير قابل للقراءة.

| الترتيب | العنصر | نوع العرض | القرار الذي يدعمه |
|---:|---|---|---|
| 1 | إجمالي الصفقات | KPI card | فهم حجم السجل الحالي |
| 2 | الصفقات المنشورة حالياً | KPI card | معرفة حجم الفرص المتاحة حالياً |
| 3 | الصفقات قيد التقييم | KPI card | تحديد حجم الملفات في مرحلة التقييم، دون حكم على التأخر |
| 4 | العروض المسجلة | KPI card | فهم حجم العروض في المنصة |
| 5 | أحداث التدقيق الموثقة | KPI card | الانتقال إلى النشاط الموثق، دون تفسيره كخطر |
| 6 | توزيع حالات الصفقات | قائمة أو bars بسيطة لاحقاً | اختيار حالة للفحص الوصفي |
| 7 | آخر النشاط الموثق | قائمة قراءة فقط | اختيار حدث أو كيان للمراجعة لاحقاً |

المؤشر الخامس هو «أحداث التدقيق الموثقة» وليس «المخاطر». أما `awarded`، رغم أنه محسوب خادمياً، فيبقى خارج الاختيار الأول حتى يُحسم موقعه في IA وعلاقته بقرارات الإدارة المركزية؛ لا توجد حاجة لإظهار كل قيمة متاحة لمجرد أنها متاحة.

### 4.2 ترتيب الصفحة المقترح

تبدأ Overview بعنوان يوضح «قراءة ومتابعة فقط»، ثم صف KPI من خمسة عناصر، ثم توزيع حالات الصفقات، ثم آخر النشاط الموثق. تكون الأقسام Trends وBid Flow وRisk وAlerts خارج الصفحة أو موسومة Future-ready إلى أن تعتمد مصادرها.

### 4.3 حالات البيانات المطلوبة عند التنفيذ

| الحالة | السلوك التخطيطي |
|---|---|
| Loading | skeleton محلي لكل KPI أو جدول، دون حجب كامل الصفحة |
| Empty | رسالة واضحة مثل «لا توجد سجلات متاحة حالياً» |
| Error | رسالة مصدر محدد مع إجراء إعادة المحاولة |
| Partial | عرض الأجزاء الناجحة مع توضيح الجزء غير المتاح |
| Forbidden | عدم عرض البيانات وإظهار أن الصلاحية غير متاحة |
| Zero | عرض `0` مع تفسير «لا توجد سجلات»، وليس `—` المضلل |

## 5. Query dependencies for a later implementation phase

هذه ليست queries منفذة، بل قائمة تبعيات يجب اعتمادها لاحقاً قبل البناء:

| الحاجة | الإجراء الحالي | القرار |
|---|---|---|
| KPI الحالية | `regulator.stats` | يعاد استخدامه كما هو مبدئياً |
| توزيع الحالات | `regulator.tenders` | يمكن استخدامه وصفياً في MVP، مع مراقبة حجم البيانات |
| آخر نشاط | `regulator.audit` | يعاد استخدامه للمعاينة المحدودة |
| `tenders_evaluation` | لا قيمة مستقلة في `stats` | يحتاج إضافة إلى stats أو تجميع خادمي لاحقاً قبل الاعتماد التنفيذي |
| Bid Flow | لا يوجد | مؤجل حتى تعريف query bids محمية |
| Trends | لا يوجد | مؤجل حتى تعريف period وgrouping |
| Audit filters | لا يوجد | مؤجل حتى تعريف filter contract وpagination |

## 6. Phase 2 decisions

أولاً، تكون Overview وصفية وليست تنبؤية، ولا تعرض أكثر من خمسة KPI رئيسية. ثانياً، لا تُبنى الرسوم قبل وجود query تجميعية تدعم dimension وperiod وempty/error states. ثالثاً، يبقى Tender Health جزءاً وصفياً من Overview في البداية، ولا يستخدم تسميات المخاطر. رابعاً، يبقى Bid Flow وTrends وAudit & Activity المفصل خارج MVP التنفيذي حتى تُعتمد مصادره الخادمية. خامساً، لا يتغير دور `regulator` ولا تُضاف صلاحية تنفيذية.

تمت مطابقة الخطة مع تقرير الاكتشاف السابق، ومخطط الحالات، وإجراءات regulator، ومصفوفة الصلاحيات. لم يتم تنفيذ UI أو chart أو query، ولذلك لم تُجرَ اختبارات واجهة جديدة في هذه المرحلة.

### NOT IMPLEMENTED

لم يتم تنفيذ أي صفحة أو sidebar أو KPI strip أو chart، ولم تتم إضافة استعلامات زمنية أو تجميعية أو فلاتر audit أو bid flow أو risk/alert logic. لم يتغير schema أو دور regulator.

### RISKS

الخطر الرئيسي هو أن `tenders_evaluation` ليس قيمة مستقلة في `regulator.stats` الحالية، ولذلك يحتاج في التنفيذ إلى قرار خادمي قبل عرضه كبطاقة. كما أن الاعتماد على قوائم كاملة للتجميع قد لا يكون مناسباً عند نمو البيانات. وأي تسميات زمنية أو تنبؤية ستظل غير صالحة ما لم تعتمد لها queries وفترات وتعريفات مستقلة.

## 8. Approval gate

هذه الوثيقة جاهزة للاعتماد قبل PHASE 3. لا ينبغي بدء تنفيذ UI قبل تأكيد أن Overview MVP، وعدد KPI، وبنية الأقسام، وحدود Future-ready، ومتطلبات queries المستقبلية مقبولة.
