# تقرير PHASE 3 — DASHBOARD SHELL

## PHASE

تم تنفيذ هيكل Dashboard Shell لبوابة المصلحة المتعاقدة داخل `/app` مع الحفاظ على المسار الموحد الحالي، وإبقاء بوابتي المتعامل الاقتصادي والإدارة المركزية دون تغيير في سلوكهما. يعتمد الهيكل على واجهة عربية RTL بنبرة مؤسسية، مع تنقل واضح بين الأقسام السبعة المعتمدة.

## DATA SOURCES

المصدر الوحيد لبيانات الصفقات في هذا الـ Shell هو `trpc.tenders.mine.useQuery()`، وهو مربوط بإجراء الخادم `tenders.mine`. المؤشرات السبعة مشتقة محلياً من الصفوف المعادة: إجمالي الصفقات، المسودات، المنشورة، المغلقة، قيد التقييم، المسندة، والملغاة. لا توجد مؤشرات زمنية أو تنبيهات أو ادعاءات تشغيلية غير موجودة في قاعدة البيانات.

## PERMISSIONS

يستخدم `tenders.mine` حارس الدور الموجود على الخادم `roleProcedure(["authority", "admin"])`، ويستعمل الخادم هوية المستخدم الحالية لتمرير `ctx.user.id` إلى `listTendersForAuthority`. لذلك لا تعتمد الواجهة وحدها على إخفاء البيانات أو الإجراءات. يغطي الاختبار الجديد قبول authority ورفض supplier وregulator لمصدر بيانات البوابة.

## VERIFICATION

نجح فحص TypeScript عبر `pnpm exec tsc --noEmit`. نجحت اختبارات Vitest: **5 ملفات و14 اختباراً**. تضمنت الاختبارات الجديدة حماية `tenders.mine` حسب الدور، بينما بقيت اختبارات دورة الصفقات والعروض والتدقيق والإدارة المركزية ناجحة. تم التقاط معاينة سطح مكتب بعرض 1280 بكسل ومعاينة هاتف بعرض 375 بكسل، وتحققت القراءة RTL والتخطيط المتجاوب بصرياً.

تم إصلاح drill-down بحيث تمرر بطاقات KPI مرشح الحالة إلى قائمة الصفقات، وأصبحت صفوف الصفقات قابلة للنقر وتقود إلى مسار منطقي بحسب الحالة: المسودات، التقييم، أو الإسناد/القرار. كما أصبحت عناصر Sidebar الخارجية تستخدم query parameters مميزة مثل `/app?section=drafts` بدلاً من تكرار `/app` فقط.

## NOT IMPLEMENTED

لم يتم تنفيذ تقارير فعلية أو إشعارات فعلية أو مستودع مستندات، لعدم وجود نماذج واستعلامات معتمدة لها ضمن MVP. لم يتم إضافة حالات جديدة إلى قاعدة البيانات. لم يتم ربط نموذج إنشاء الصفقة التشغيلي داخل الـ Shell الجديد؛ المدخل الحالي يوضح بصدق أنه سيُربط في المرحلة التالية بدلاً من اختراع تدفق جديد. كما أن فتح العروض التفصيلية والتقييم والإسناد ما زال يعتمد على المسارات التشغيلية القائمة في البوابة القديمة إلى حين تنفيذ مرحلة Implementation التالية.

## RISKS

المسارات الحالية تستخدم `/app` مع query parameter للحفاظ على التوافق، ولذلك لا تزال نقطة الدخول موحدة وليست routes مستقلة بالكامل. التنقل الداخلي في `AuthoritySidebar` يغير حالة العرض محلياً، بينما التنقل من Sidebar العام يعتمد على query parameter؛ ينبغي توحيد ذلك في المرحلة التالية إذا أصبحت الأقسام صفحات مستقلة. كما ينبغي اختبار drill-down على حساب authority حقيقي يحوي صفقات في حالات متعددة قبل اعتماد المرحلة التشغيلية التالية.
