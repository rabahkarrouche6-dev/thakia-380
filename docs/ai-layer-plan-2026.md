# خطة إضافة طبقة الذكاء الاصطناعي إلى منصة «صفقات ذكية»

**الإصدار:** 1.0  
**التاريخ:** 21 أوت 2026  
**النطاق:** بوابات الإدارة المركزية، المصلحة المتعاقدة، والمتعامل الاقتصادي  
**المبدأ الحاكم:** الذكاء الاصطناعي يقدّم إرشاداً وتحليلاً قابلاً للمراجعة، ولا يستبدل القرار البشري أو الصلاحيات القانونية.

## 1. الملخص التنفيذي

تقترح هذه الخطة بناء طبقة ذكاء اصطناعي تدريجية فوق البنية الحالية لمنصة «صفقات ذكية»، تبدأ بميزات منخفضة المخاطر وعالية القيمة، ثم تتوسع بعد إثبات الدقة والسلامة. توجد بالفعل خدمة استشارية في `server/aiAssistant.ts` ومساعد قانوني مقيد بالمراجع الرسمية؛ لذلك لا يُنصح بإنشاء تكامل منفصل، بل بتوحيد هذه القدرات خلف طبقة خدمات واحدة تتضمن إدارة السياق، الاسترجاع الموثق، حواجز السلامة، سجل التدقيق، والتقييم.

يُنفذ الإصدار الأول دون اتخاذ إجراءات تلقائية في الصفقات أو العروض أو الترسية. كل اقتراح يجب أن يعرض مصدره ودرجة الثقة وحدوده، وأن يتيح للمستخدم المخول قبول النتيجة أو تعديلها أو رفضها يدوياً.

## 2. الأهداف والحدود

الهدف هو تقليل الوقت اللازم للبحث والفهم والتحقق وإعداد المسودات، مع رفع قابلية التتبع وتحسين الوصول إلى المعلومات. لا تهدف الطبقة إلى منح الأهلية، ترتيب المتعاملين تلقائياً، تغيير آجال أو شروط صفقة، إصدار قرار ترسية، أو إرسال وثيقة رسمية نيابة عن المستخدم.

| المجال | داخل النطاق | خارج النطاق في الإصدار الأول |
|---|---|---|
| المعرفة | البحث في القوانين والوثائق المصرح بها وإظهار المصادر | الإجابة من ذاكرة النموذج دون مصدر قابل للتحقق |
| التحليل | تلخيص، استخراج حقول، كشف نقص شكلي، مقارنة وثائق | قرار قبول/رفض أو تقييم نهائي للعروض |
| الإنتاج | مسودات قابلة للتحرير مع سجل تغييرات | نشر أو توقيع أو إرسال تلقائي |
| التشغيل | مساعد محادثة واستعلامات مقيدة بالدور | وكيل مستقل ينفذ إجراءات حساسة |
| البيانات | بيانات مصرح للمستخدم بالوصول إليها فقط | خلط بيانات جهات أو متعاملين مختلفين |

## 3. حالات الاستخدام ذات الأولوية

### 3.1 الإدارة المركزية

تحتاج الإدارة المركزية إلى طبقة تلخص مؤشرات الصفقات والاعتمادات والتنبيهات، وتساعد في اكتشاف الأنماط غير الاعتيادية دون إصدار أحكام نهائية. تبدأ الميزات بمساعد استعلام عن المؤشرات، تلخيص طلبات الاعتماد، وتجميع التنبيهات المتشابهة مع روابط إلى السجلات الأصلية.

### 3.2 المصلحة المتعاقدة

تكون الأولوية لمسودة دفتر الشروط من قوالب معتمدة، قائمة تحقق قبل النشر، تلخيص مراحل الصفقة، وتنبيه المستخدم إلى الحقول أو الوثائق الناقصة. يجب أن تعرض كل نتيجة كمسودة أو قائمة تحقق، مع تأكيد صريح قبل حفظها في النظام.

### 3.3 المتعامل الاقتصادي

تبدأ الميزات بمساعد فهم شروط المشاركة، تلخيص الفرص والآجال، شرح حالة العرض أو العقد بلغة واضحة، وقائمة تحقق للوثائق التي أدخلها المستخدم. لا يجوز للمساعد أن يعد بالفوز أو الأهلية، ولا أن يغير العرض أو يرسله دون مراجعة المستخدم.

### 3.4 الإطار القانوني

يُطوّر المساعد القانوني الحالي ليجيب فقط من سجل مراجع قانونية معتمد، ويعرض اسم المرجع ورابطه ومقطع الاستناد أو سبب عدم كفاية المعلومات. عند غياب مصدر مناسب، يجب أن يصرح بعدم كفاية المرجع بدلاً من توليد إجابة تخمينية.

| الأولوية | الميزة | القيمة | مستوى المخاطر | قرار التنفيذ |
|---|---|---:|---:|---|
| P0 | البحث القانوني الموثق مع المصادر | مرتفعة | منخفض | يبدأ أولاً |
| P0 | تلخيص الوثائق وقوائم التحقق | مرتفعة | منخفض/متوسط | يبدأ بعد طبقة المصادر |
| P1 | مساعد المؤشرات والتنبيهات | مرتفعة | متوسط | بعد ضبط عزل البيانات |
| P1 | مسودات دفتر الشروط والردود | مرتفعة | متوسط | مع مراجعة بشرية إلزامية |
| P2 | كشف الشذوذ في آجال وقيم الصفقات | متوسطة | مرتفع | تجريبي، دون قرار آلي |
| P3 | وكيل ينفذ إجراءات متعددة الخطوات | غير ضرورية للإصدار الأول | مرتفع جداً | مؤجل حتى نضج الحوكمة |

## 4. المعمارية المقترحة

تتكون الطبقة من ستة مكونات منطقية، مع إبقاء مفاتيح النماذج والخدمات في الخادم وعدم كشفها في الواجهة الأمامية.

1. **AI Gateway:** نقطة موحدة تستقبل الطلبات المصرح بها، تتحقق من الدور والجهة ونوع المهمة، وتطبق حدود الحجم والزمن والتكلفة.
2. **Context Builder:** يبني سياقاً من بيانات المستخدم المسموح بها فقط، مع إخفاء الحقول الحساسة وتقليل البيانات إلى الحد اللازم.
3. **Retrieval Layer:** يسترجع الوثائق والمراجع من مصادر معتمدة ومفهرسة، ويرفق كل مقطع بمعرف المصدر والإصدار وتاريخ التحديث.
4. **Prompt and Policy Layer:** قوالب منفصلة لكل دور ومهمة، تتضمن منع اتخاذ القرار، منع كشف البيانات العابرة للجهات، واشتراط ذكر الحدود والمصادر.
5. **Model Adapter:** يستدعي النموذج الحالي عبر `invokeLLM` خلف واجهة قابلة لتبديل النموذج، مع fallback واضح عند عدم توفر الخدمة.
6. **Audit and Evaluation:** يسجل نوع المهمة، الدور، المصادر، زمن الاستجابة، النتيجة المهيكلة، وقرار المستخدم اللاحق دون حفظ أسرار أو نصوص حساسة أكثر من اللازم.

يُقترح تنظيم الخادم لاحقاً في وحدات مثل `server/ai/gateway.ts` و`server/ai/policies.ts` و`server/ai/retrieval.ts` و`server/ai/evaluation.ts`، مع الإبقاء على `server/aiAssistant.ts` كواجهة توافق مؤقتة إلى حين نقل الاستخدامات الحالية تدريجياً.

## 5. البيانات والاسترجاع الموثق RAG

لا ينبغي تدريب نموذج مخصص على بيانات المنصة في البداية. الأفضل إنشاء فهرس استرجاع للوثائق المعتمدة، مع بيانات وصفية تشمل نوع الوثيقة، الجهة المالكة، الإصدار، تاريخ السريان، مستوى السرية، ونطاق الأدوار المسموح لها بالوصول. تُفصل فهارس الإطار القانوني العام عن بيانات الصفقات والوثائق الخاصة بكل جهة.

قبل إدخال أي وثيقة إلى الفهرس، تمر عبر مسار اعتماد يتضمن فحص النوع والحجم، إزالة البيانات غير الضرورية، تحديد المالك، استخراج النص، اختبار جودة OCR عند الحاجة، ومراجعة بشرية للمصدر. لا تُستخدم وثيقة منتهية أو غير معتمدة للإجابة دون وسم واضح.

## 6. الأمن والخصوصية وRBAC

يجب أن يطبق الخادم عزل الجهة قبل الاسترجاع، لا بعد توليد الإجابة. يمر كل طلب عبر `protectedProcedure` أو سياسة دور مكافئة، ثم يتحقق من ملكية السجل ونطاق المؤسسة. لا يكفي إخفاء زر المساعد في الواجهة. كما يجب منع تمرير الأسرار، رموز الجلسات، مفاتيح API، كلمات المرور، والبيانات الشخصية غير اللازمة إلى النموذج.

| الضابط | المتطلب |
|---|---|
| المصادقة | المستخدم المسجل فقط للبيانات الخاصة؛ المساعد القانوني العام يظل مقيداً بالمصادر العامة |
| التفويض | فحص الدور والجهة والملكية قبل بناء السياق والاسترجاع |
| عزل البيانات | لا تُستخدم نتائج أو وثائق جهة في سياق جهة أخرى |
| التسجيل | سجل تدقيق للطلب والمصادر والقرار، مع تقليل النصوص الحساسة |
| الأسرار | الخادم فقط؛ لا أسرار أو مفاتيح في React أو localStorage |
| الاحتفاظ | سياسة احتفاظ محددة وقابلة للمسح، مع فصل سجلات التقييم عن بيانات الإنتاج |
| الإخفاق | fallback آمن ورسالة صريحة، دون اختلاق مصدر أو نتيجة |

## 7. تصميم تجربة المستخدم

يظهر المساعد داخل كل بوابة بصيغة مرتبطة بالسياق الحالي، لا كنافذة عامة غامضة. يبدأ المستخدم من اقتراحات جاهزة مرتبطة بدوره، ثم يرى مصادر الإجابة والقيود والإجراءات التالية. يجب أن تتضمن كل نتيجة شارة «استشاري»، ووقت التوليد، وروابط السجلات أو الوثائق الأصلية، وأزرار «نسخ»، «طلب مراجعة»، و«إبلاغ عن إجابة غير دقيقة».

عند إنشاء مسودة أو قائمة تحقق، تُعرض النتيجة في مساحة مراجعة منفصلة. لا تُحفظ في النظام إلا بعد تأكيد المستخدم المخول، مع إبقاء النسخة الأصلية وسجل التعديلات. وفي حالات عدم كفاية البيانات، تظهر حالة واضحة تقترح الوثيقة أو الحقل المطلوب بدلاً من إجابة واثقة زائفة.

## 8. خارطة التنفيذ المرحلية

| المرحلة | المحتوى | مخرجات القبول |
|---|---|---|
| المرحلة 0: الأساس | توحيد Gateway والسياسات، تعريف أنواع المهام، حدود الحجم والزمن، وسجل التدقيق | كل استدعاء يمر عبر سياسة موحدة ولا يكشف أسراراً |
| المرحلة 1: مصادر موثقة | فهرس قانوني معتمد، استرجاع بمصادر، تحديث وإبطال الوثائق | إجابة قانونية لا تُقبل دون مصدر أو رسالة عدم كفاية |
| المرحلة 2: مساعد البوابات | تلخيص وقوائم تحقق لكل دور، سياق محمي، حالات loading/error/empty | لا يرى المستخدم إلا بيانات دوره، وكل مسودة تحتاج تأكيداً |
| المرحلة 3: التحليلات | ملخصات المؤشرات وتجميع التنبيهات ومقارنات زمنية وصفية | لا يوجد ترتيب أو قرار آلي، وكل مؤشر قابل للتتبع |
| المرحلة 4: تجريب مضبوط | إطلاق اختياري لمجموعة مستخدمين، قياس الدقة والرفض والتكلفة | تجاوز عتبات الجودة والسلامة قبل التوسع |
| المرحلة 5: التوسع | تحسين النماذج، قوالب أكثر، مراقبة مستمرة، تدريب المستخدمين | مراجعة شهرية للسياسات والمصادر والنتائج |

## 9. الاختبارات والتقييم

تُكتب اختبارات وحدات للعزل والصلاحيات وتطبيع المدخلات وتحقق معرفات المصادر، واختبارات عقود لإجراءات tRPC، واختبارات تكامل لمسار الاسترجاع والمساعد. يجب أن تتضمن المجموعة حالات محاولة الوصول إلى وثيقة جهة أخرى، سؤال خارج النطاق، مصدر منتهٍ، نص ضخم، prompt injection داخل وثيقة، وانقطاع مزود النموذج.

يقاس الأداء على مجموعة تقييم داخلية غير إنتاجية تحتوي على أسئلة عربية وفرنسية واقعية بعد تنقيحها. تُراجع النتائج بشرياً وفق معايير صحة المصدر، اكتمال الإجابة، وضوح الحدود، عدم الاختلاق، وعدم تسريب البيانات. لا تُستخدم بيانات أو تقييمات مصطنعة للإعلان عن دقة النظام.

| المؤشر | طريقة القياس | عتبة أولية مقترحة |
|---|---|---:|
| صحة الإسناد | نسبة الإجابات التي تشير إلى مصدر مناسب فعلاً | 95% في نطاق القانون |
| الاختلاق | إجابات بلا سند أو معلومات غير موجودة | أقل من 2% في مجموعة التقييم |
| سلامة الصلاحيات | حالات تسريب عبر الجهات أو الأدوار | صفر حالات حرجة |
| قابلية الاستخدام | نجاح المستخدم في إتمام المهمة بعد المساعدة | يحدد بخط أساس قبل التجربة |
| زمن الاستجابة | p95 للاستعلامات العادية | يحدد من القياس الحالي ثم يحسن |
| التكلفة | تكلفة كل مهمة حسب النوع والدور | حد شهري ومعدل تنبيه واضح |

هذه العتبات ليست اعتماداً نهائياً؛ يجب تثبيتها بعد قياس خط الأساس ومراجعة مسؤول المنتج والأمن والامتثال.

## 10. التشغيل والمراقبة

تُراقب الطلبات حسب نوع المهمة والدور والمدة وحالة fallback، مع تنبيهات عند ارتفاع الأخطاء أو التكلفة أو محاولات تجاوز السياسة. تُحفظ نسخة القالب وإصدار مصدر المعرفة المستخدم لكل إجابة حتى يمكن إعادة تفسيرها. يجب توفير مفتاح إيقاف سريع لكل ميزة ذكاء اصطناعي دون تعطيل البوابات الأساسية.

يُفضل إطلاق المزايا خلف feature flags، بدءاً بالمساعد القانوني والملخصات، ثم فتحها اختيارياً لمستخدمين محددين. تُراجع عينة دورية من الإجابات، وتُسجل ملاحظات المستخدمين، وتُغلق الميزة تلقائياً إذا ظهرت مشكلة سلامة حرجة.

## 11. المسؤوليات والحوكمة

يتولى مالك المنتج تحديد المهام المقبولة، ويتولى مسؤول الأمن مراجعة العزل وتسرب البيانات، ويتولى المسؤول القانوني اعتماد مصادر الإطار القانوني، ويتولى فريق التطوير الاختبارات والمراقبة، بينما يظل المستخدم المخول مسؤولاً عن القرار النهائي داخل النظام. أي استخدام جديد لبيانات حساسة أو أي تغيير إلى تنفيذ آلي يحتاج موافقة منفصلة قبل التطوير.

## 12. القرار الأول المقترح

البدء بحزمة صغيرة من ثلاث ميزات: **مساعد قانوني موثق بالمصادر، ملخصات وقوائم تحقق للوثائق، ومساعد مؤشرات وصفي للمصلحة المتعاقدة**. تنفذ الحزمة عبر Gateway موحد، دون migrations جديدة إلا عند اعتماد سجل التدقيق ونموذج المعرفة، ودون تغيير OAuth أو RBAC القائمين. بعد ذلك تُجرى تجربة محدودة، وتُعرض نتائج الجودة والسلامة والتكلفة على أصحاب القرار قبل الانتقال إلى التحليلات المتقدمة.

## 13. قرارات مفتوحة قبل التنفيذ

| القرار | الخيارات | التوصية |
|---|---|---|
| نطاق المعرفة | مصادر قانونية فقط / وثائق تشغيلية أيضاً | البدء بالمصادر القانونية والوثائق المعتمدة |
| التخزين | سجل تدقيق مستقل / توسيع جداول المستخدم | سجل مستقل بعد مراجعة الخصوصية |
| اللغات | العربية فقط / العربية والفرنسية | العربية أولاً مع تصميم قابل للتوسع للفرنسية |
| التشغيل | للجميع / feature flag / دعوة محدودة | feature flag ودعوة محدودة |
| الحفظ | نتيجة مؤقتة / مسودة قابلة للمراجعة | مسودة قابلة للمراجعة دون نشر تلقائي |

> **قاعدة غير قابلة للتفاوض:** لا يُعتبر أي مسار ذكاء اصطناعي مكتملاً ما لم يحقق التحقق من الهوية والصلاحية، وعزل البيانات، وإظهار المصادر والحدود، وحالات التحميل والخطأ والفراغ، واختباراً بشرياً قابلاً للتدقيق.


## 14. حزمة دفاتر الشروط المدفوعة

تُضاف حزمة **دفاتر الشروط الذكية** كميزة مدفوعة اختيارية، ولا تُفتح إلا للمستخدم الذي يملك اشتراكاً فعالاً أو صلاحية مؤسسية مكافئة. الدفع يفتح الوصول إلى أدوات إعداد المسودة فقط؛ ولا يمنح الذكاء الاصطناعي صلاحية النشر أو الاعتماد أو الالتزام القانوني نيابة عن المستخدم.

### 14.1 مسار المتعامل الاقتصادي: ملء دفتر الشروط

يبدأ المتعامل من دفتر شروط معتمد أو نموذج رسمي تتيحه المصلحة، ثم يطلب من المساعد اقتراح تعبئة الحقول اعتماداً على بيانات ملفه المؤسسي والوثائق التي رفعها وصلاحياته. يوضح النظام لكل حقل مصدر القيمة ودرجة اكتمالها، ويميز بين **قيمة مستخرجة** و**قيمة مقترحة** و**حقل يحتاج إدخالاً بشرياً**. لا يجوز للمساعد اختراع أرقام أو شهادات أو خبرات أو التزامات غير موجودة في المستندات.

ينتج المسار مسودة قابلة للتحرير مع قائمة نواقص، وفحوص اتساق، وتنبيه إلى الحقول الحساسة مثل المبالغ والآجال والمراجع القانونية. لا تُرسل المسودة إلى المصلحة ولا تُعتبر عرضاً رسمياً إلا بعد مراجعة المتعامل وتأكيده الصريح وفق المسار التشغيلي المعتمد.

### 14.2 مسار المصلحة المتعاقدة: توليد دفتر الشروط

تدخل المصلحة المتعاقدة معطيات الصفقة المعتمدة، مثل موضوعها، الحاجات، الميزانية التقديرية، الجدول الزمني، معايير التقييم، الشروط الإدارية والتقنية، والقيود القانونية ذات الصلة. يسترجع المساعد القوالب الرسمية والمراجع المسموح بها، ثم يولد **مسودة دفتر شروط** منظمة حسب القالب المعتمد، مع إحالات مصدرية وتعليقات تفسيرية منفصلة عن النص المقترح.

يجب أن يعرض النظام قبل التوليد ملخصاً للمدخلات الناقصة والتعارضات المحتملة. وبعد التوليد، يمر دفتر الشروط عبر قائمة تحقق إلزامية تشمل اكتمال الأقسام، اتساق المعايير والأوزان، قابلية التتبع إلى المدخلات، عدم وجود شروط تمييزية ظاهرة، وصحة الإحالات القانونية بحسب آخر نسخة معتمدة. تبقى المسودة في حالة **قيد المراجعة** ولا تُنشر أو تعتمد تلقائياً.

### 14.3 حالات العمل والضوابط

| الحالة | الوصف | الإجراء المسموح |
|---|---|---|
| مسودة أولية | تم جمع المدخلات ولم يبدأ التوليد أو الملء | تعديل المدخلات وطلب اقتراح |
| مولدة بالذكاء الاصطناعي | أُنشئت مسودة مع مصادر ونسخة النموذج | مراجعة وتحرير وتعليق |
| تحتاج تدقيقاً | توجد حقول ناقصة أو تعارضات أو مصادر غير كافية | تصحيح المدخلات أو طلب مراجعة بشرية |
| جاهزة للمراجعة الرسمية | اجتازت الفحوص التقنية ولم تعتمد قانونياً | إرسالها للمستخدم المخول فقط |
| معتمدة/منشورة | قرار بشري موثق خارج نطاق التوليد الآلي | تنفيذ المسار التشغيلي العادي |

### 14.4 حدود الحزمة المدفوعة

تُقاس الحصة بعدد عمليات التوليد أو الصفحات أو الدقائق المعالجة، مع إظهار الاستهلاك والتكلفة المتوقعة قبل التنفيذ. تُطبق حدود للملفات والحجم ومعدل الطلبات، ويُتاح fallback يدوي عند فشل النموذج. تُحفظ إصدارات المسودة ومصادرها وسجل المراجعة، ولا تُستخدم وثائق المتعامل أو المصلحة لتدريب نموذج عام دون موافقة صريحة وسياسة منفصلة.

تحتاج هذه الحزمة قبل التنفيذ إلى اعتماد مزود الدفع المحلي أو بوابة الدفع المختارة، تعريف خطط الاشتراك وسياسة الإلغاء والاسترداد، تحديد القوالب الرسمية المسموح بها، واعتماد المسؤول القانوني وقائمة مراجعة المصلحة. كما تحتاج إلى قرار مستقل بشأن ما إذا كانت المسودات تحفظ في سجل دائم أو مساحة مؤقتة، وبشأن مدة الاحتفاظ بالوثائق الحساسة.

### 14.5 مراحل التنفيذ المقترحة

1. بناء نموذج بيانات للمسودة والإصدار والمصدر وسجل المراجعة، دون ربطه بالنشر التلقائي.
2. إطلاق تعبئة المتعامل لدفتر معتمد في وضع تجريبي محدود، مع استخراج محافظ ومراجعة حقلية.
3. إضافة مولد المصلحة لقالب واحد مع قائمة تحقق واعتماد بشري إلزامي.
4. ربط الحزمة بنظام الاشتراك والدفع بعد اعتماد المزود والسياسات، مع بوابة صلاحيات مستقلة.
5. توسيع القوالب واللغات فقط بعد قياس الدقة والاستكمال ومعدل التصحيح وحوادث السلامة.

> **قاعدة حاكمة:** الذكاء الاصطناعي يكتب مسودة ويشرح مصادرها؛ المستخدم المخول وحده يراجع ويعتمد وينشر، ولا يجوز تحويل الدفع إلى تجاوز للصلاحيات أو للرقابة القانونية.
