# CENTRAL ANALYTICS DISCOVERY

**المرحلة:** PHASE 1 فقط — الاكتشاف  
**النطاق:** فحص بوابة `regulator` الحالية، استعلامات الإحصاءات، سجل التدقيق، حالات الصفقات، المكونات، اختبارات الصلاحيات، وأي رسوم بيانية موجودة.  
**القرار التنفيذي:** لم تُنفذ أي واجهة، ولم تُضف أي query أو migration أو chart.

## PHASE

بوابة الإدارة المركزية الحالية هي امتداد للدور الخادمي `regulator` داخل المسار الموحد `/app`. في `client/src/pages/Portal.tsx` يتم توجيه المستخدم ذي الدور `regulator` إلى `CentralAdminPortal` مع عنوان «مرصد الإدارة المركزية». التنقل الحالي محدود إلى «لوحة المؤشرات» و«سجل التدقيق»، وكلاهما يعمل ضمن `/app`.

المكوّن `client/src/pages/CentralAdminPortal.tsx` هو شاشة واحدة تجمع أربع وظائف وصفية: بطاقات مؤشرات، مراقبة الصفقات، توزيع الحالات، وآخر أحداث التدقيق. كما تحتوي على مساعد إرشادي معلن بوضوح أنه لا يتخذ قراراً تعاقدياً. لا توجد في الشاشة الحالية رسوم زمنية أو رسوم بيانية تفاعلية؛ البحث والتصفية محليان داخل قائمة الصفقات، وتوزيع الحالات يُحسب محلياً من البيانات المحملة.

## DATA SOURCES

المصادر الفعلية ذات الصلة هي `tenders` و`bids` و`auditLogs`، مع وجود `users` و`awardDecisions` في المخطط دون إجراءات تحليلية مركزية حالية لهما.

| المصدر | الحقول ذات الصلة | الاستعمال الحالي |
|---|---|---|
| `tenders` | `status`, `category`, `location`, `budget`, `authorityId`, `createdAt`, `publishedAt`, `closedAt`, `deadline` | قائمة الصفقات، إجمالي الصفقات، المنشورة، وتوزيع الحالات |
| `bids` | `tenderId`, `supplierId`, `amount`, `status`, `submittedAt`, `evaluatedAt` | إجمالي العروض فقط عبر `stats`؛ لا يوجد توزيع مركزي للعروض |
| `auditLogs` | `actorId`, `action`, `entityType`, `entityId`, `result`, `metadata`, `createdAt` | آخر نشاط موثق بحد أقصى 50 سجلاً |
| `awardDecisions` | `decision`, `winningBidId`, `decidedBy`, `decidedAt` | موجود في schema، ولا توجد query regulator لعرضه |
| `users` | `role`, `createdAt`, `lastSignedIn` | لا توجد query regulator لعدد المستخدمين أو النشاط حسب الدور |

## EXISTING STATS QUERIES

في `server/routers.ts` توجد الإجراءات التالية، وكلها محمية بواسطة `roleProcedure(["regulator", "admin"])`:

| الإجراء | المساعد | السلوك الفعلي |
|---|---|---|
| `regulator.stats` | `getPlatformStats()` | يعيد `tenders`, `published`, `bids`, `awarded`, `audits` |
| `regulator.audit` | `listAuditLogs()` | يعيد آخر 50 حدثاً مرتبة تنازلياً حسب `createdAt` |
| `regulator.tenders` | `listAllTenders()` | يعيد جميع الصفقات مرتبة تنازلياً حسب `createdAt` |

`getPlatformStats()` يحسب القيم من الصفوف الفعلية. قيمة `awarded` محسوبة في الخادم لكنها غير مستخدمة في بطاقة الواجهة الحالية. لا توجد في أي من هذه الإجراءات فلاتر زمنية، أو مقارنة بفترة سابقة، أو تجميع حسب فئة أو موقع أو جهة أو مورد.

## STATUS ENUMS

حالات الصفقات الفعلية في `drizzle/schema.ts` هي:

| القيمة | التسمية الحالية |
|---|---|
| `draft` | مسودة |
| `published` | منشورة |
| `closed` | مغلقة |
| `evaluation` | قيد التقييم |
| `awarded` | مسندة |
| `cancelled` | ملغاة |

وحالات العروض هي `submitted` و`under_review` و`accepted` و`rejected`. وقرارات الإسناد هي `awarded` و`cancelled`. لا توجد حالات تحليلية إضافية مثل «متأخرة» أو «عالية المخاطر» أو «مزدحمة»؛ لذلك لا يجوز عرضها كحالات قاعدة بيانات أو كتصنيفات فعلية.

## AUDIT LOGS

يتم تسجيل أحداث فعلية عند إنشاء الصفقة، نشرها، إغلاقها، بدء تقييم العروض، تقديم عرض، تقييم عرض، إسناد صفقة، إلغاء صفقة، وتحديث الملف. كل حدث يتضمن الفاعل والعملية ونوع الكيان والمعرّف والنتيجة والوقت، وقد يتضمن `metadata` نصياً.

الإمكانية الحالية هي عرض **نشاط موثق للقراءة فقط**. لا توجد query تقبل فلاتر `action` أو `entityType` أو `result` أو نطاق تاريخ. كما لا يجوز تفسير عدد أحداث التدقيق بوصفه درجة مخاطر أو دليلاً على شبهة؛ فهو عدد السجلات الموثقة فقط.

## CHARTS

تم فحص مراجع الواجهة والخادم بحثاً عن مكتبات أو مكونات رسوم مثل `recharts` و`ChartContainer` و`BarChart` و`LineChart` و`AreaChart` و`PieChart` و`ResponsiveContainer`. لا توجد charts مستخدمة في بوابة regulator الحالية، ولا توجد مكونات رسوم تحليلية منفذة ضمن الشاشة الحالية. الموجود هو عرض بطاقات وقائمة وأزرار توزيع حالات.

بالتالي، لا توجد رسوم يمكن تقييم دقتها أو إعادة استخدامها في هذه المرحلة. أي chart لاحق يحتاج أولاً إلى تعريف query وperiod وdimension وempty/error states، ولا ينبغي بناؤه من القوائم المحملة محلياً إذا كان المقصود قياس اتجاهات.

## KPI DEFINITIONS

المؤشرات الحالية الآمنة هي مؤشرات حالة وصفية فقط:

| KPI | التعريف | المصدر | الحالة |
|---|---|---|---|
| إجمالي الصفقات | عدد صفوف `tenders` | `regulator.stats` | مستخدم في الواجهة |
| الصفقات المنشورة | عدد صفوف `tenders` ذات `status = published` | `regulator.stats` | مستخدم في الواجهة |
| العروض المسجلة | عدد صفوف `bids` | `regulator.stats` | مستخدم في الواجهة |
| أحداث التدقيق | عدد صفوف `auditLogs` | `regulator.stats` | مستخدم في الواجهة |
| توزيع حالات الصفقات | عدّ محلي لكل قيمة status | `regulator.tenders` | مستخدم في الواجهة |
| الصفقات المسندة | عدد صفوف ذات `status = awarded` | محسوب خادمياً لكنه غير معروض | مرشح لاحقاً، لا يُنفذ الآن |

لا تدعم البيانات أو الاستعلامات الحالية مؤشرات «النمو»، أو «التباطؤ»، أو «متوسط مدة المعالجة»، أو «عدد الموردين النشطين»، أو «معدل التنافس»، أو «درجة المخاطر». هذه المؤشرات تحتاج تعريفاً زمنياً واستعلامات وتجميعاً واختبارات قبل عرضها.

## PERMISSIONS

اختبارات `server/permissions.test.ts` تثبت أن regulator يستطيع استدعاء إجراءات القراءة المركزية الثلاثة، ولا يستطيع استدعاء `tenders.mine` الخاصة بملكية authority. كما تمنعه الخوادم من `tenders.create`, `tenders.publish`, `tenders.close`, `tenders.startEvaluation`, `bids.evaluate`, و`awards.decide`.

هذا يثبت أن الإدارة المركزية في MVP هي **قراءة ومراجعة فقط**. أي query تحليلية مستقبلية يجب أن تبقى خلف حارس regulator/admin، وأن تعيد أقل قدر لازم من البيانات، وألا تمنح drill-down صلاحيات تنفيذية أو تعدل الملكية الخادمية.

## NOT IMPLEMENTED

لم يتم تنفيذ Overview جديدة، ولا Trends، ولا Tender Health، ولا Bid Flow، ولا Audit & Activity مفصلة، ولا أي chart، ولا فلاتر خادمية، ولا alert logic، ولا risk scoring، ولا predictive أو AI claims، ولا تعديل schema. هذه العناصر تبقى خارج PHASE 1.

## RISKS

الخطر الأساسي هو بناء تحليلات من counts كلية بلا سياق زمني. كما أن استخدام `listAllTenders()` و`listAuditLogs()` كحل دائم قد يسبب مشاكل حجم وأداء، ولا يحقق pagination أو فلاتر خادمية. وجود جدول أو حقل في schema لا يعني أن هناك query مركزية آمنة ومهيأة للعرض.

كذلك لا توجد تواريخ كاملة لكل انتقال حالة، لذلك لا يمكن استنتاج التأخر أو مدة المعالجة من الحقول الحالية. ولا يجوز استخدام `metadata` النصي كُبعد تحليلي رسمي قبل تعريف parsing مضبوط. وأخيراً، لا ينبغي تحويل عدد سجلات التدقيق إلى درجة خطر أو اتهام.

## CONCLUSION

المنصة تملك أساساً صالحاً لعرض Overview وصفية محدودة: إجمالي الصفقات، المنشور حالياً، العروض المسجلة، توزيع الحالات، وآخر النشاط الموثق. لا تملك بعد أساساً موثوقاً للاتجاهات الزمنية أو الرسوم أو التنبيهات أو مؤشرات المخاطر.

بناءً على ذلك، انتهت **PHASE 1 — CENTRAL ANALYTICS DISCOVERY** دون تنفيذ واجهة. الخطوة التالية، بعد اعتماد المستخدم، هي PHASE 2 لتحديد Information Architecture وتعريف KPI وعقود الاستعلامات قبل أي بناء بصري.
