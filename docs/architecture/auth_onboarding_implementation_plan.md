# AUTH & ONBOARDING IMPLEMENTATION PLAN

## 1. قرار النطاق

هذه الوثيقة تحوّل موجز التصميم المرفق إلى خطة قابلة للتنفيذ، لكنها لا تنفذ أي واجهة أو خدمة جديدة. يعتمد المسار الحالي للمنصة على **Manus OAuth**، وصفحة دخول موحدة، واختيار البوابة، ثم فرض الدور والصلاحيات على الخادم. لذلك يجب ألا توحي الواجهة الحالية بوجود كلمات مرور محلية أو تسجيل حسابات عامة أو OCR أو MFA أو تسجيل عبر Google/LinkedIn ما لم تُعتمد عقود وخدمات حقيقية لهذه القدرات.

## 2. الوضع الحالي الموثق

| المجال | المتاح فعلياً | حدود الوضع الحالي |
|---|---|---|
| الدخول | مسارات `/login` و`/login/supplier` و`/login/authority` و`/login/regulator` مع Manus OAuth | لا توجد إدارة كلمة مرور محلية داخل المنصة |
| اختيار البوابة | اختيار سياق البوابة قبل بدء الدخول | الدور النهائي يحدده الخادم ولا يجوز للواجهة فرضه |
| الجلسة | `auth.me` وسياق مستخدم محمي وتسجيل خروج | لا يوجد إنشاء حساب عام من داخل المنصة |
| الصلاحيات | عزل supplier وauthority وregulator على الخادم | لا تُستبدل الصلاحيات بإخفاء عناصر الواجهة فقط |
| العودة | زر مركزي «العودة إلى صفحة التسجيل» في الغلاف المصادق | لا يظهر في صفحة الدخول أو الصفحات غير المصادق عليها |
| التهيئة | لا يوجد Onboarding متعدد الخطوات منفذ | لا توجد بعد نماذج تهيئة مؤسسية أو دعوات فرق |

## 3. Information Architecture المقترحة

### المتعامل الاقتصادي

يبدأ المسار من `/login/supplier` ثم Manus OAuth. بعد نجاح الدخول ينتقل المستخدم إلى `/app` مع بوابة المورد التي يحددها الدور الخادمي. يمكن لاحقاً إضافة صفحة تهيئة منفصلة للملف المؤسسي، لكنها يجب أن تعتمد على `profile.get` و`profile.save` وحقول موجودة فعلياً فقط. رفع سجل تجاري أو استخراج اسم الشركة ورقم التسجيل ورأس المال عبر OCR خارج النطاق الحالي.

### المصلحة المتعاقدة

يبدأ المسار من `/login/authority` ثم Manus OAuth، وبعد التحقق ينتقل المستخدم إلى مساحة authority الحالية. إعداد Workspace، شعار المؤسسة، دعوات الفريق، وتوزيع أدوار إضافية ليست عقوداً متاحة حالياً، ولذلك تُصنف كمرحلة مستقلة تحتاج نماذج وصلاحيات واستعلامات قبل تصميمها.

### الإدارة المركزية

يبدأ المسار من `/login/regulator` ثم Manus OAuth، مع استمرار اعتماد الحسابات التي يديرها مزود الدخول. لا يُقترح إنشاء حساب عام. MFA والقياسات الحيوية وعبارات الأمان السيبراني لا تُعرض كقدرات منفذة قبل أن يوفرها مزود المصادقة أو تُضاف بعقد أمني معتمد.

## 4. مراحل التنفيذ المقترحة بعد الاعتماد

| المرحلة | المحتوى | شرط البدء |
|---|---|---|
| A | تحسين تجربة صفحات الدخول الحالية: اختيار البوابة، شرح مختصر، مساعدة، حالات loading/error، وروابط العودة | العقود الحالية فقط؛ لا تغيير OAuth |
| B | Onboarding المورد بالحقول الموجودة في ملف المورد، مع حفظ صريح وحالات تحقق | اعتماد قاموس حقول profile وحدود التحقق |
| C | Onboarding المصلحة المتعاقدة ومساحة العمل ودعوات الفريق | إضافة نماذج وقواعد ملكية وصلاحيات حقيقية |
| D | تهيئة الإدارة المركزية الأمنية | اعتماد MFA من مزود المصادقة أو خدمة مؤسسية موثقة |
| E | OCR ورفع المستندات وموفرو الدخول الخارجيون | اعتماد التخزين، الخصوصية، التكاملات، والاختبارات الأمنية |

## 5. خريطة المكونات المقترحة

المكونات القابلة للتنفيذ أولاً هي `LoginPortalSelector` و`AuthStatusPanel` و`OnboardingProgress` كعناصر عرضية مرتبطة بسياق المصادقة الحالي، مع الحفاظ على `Login.tsx` و`DashboardLayout`. لا ينبغي إنشاء `DocumentScanner` أو `OCRAutofill` أو `MFAChallenge` أو `TeamInviteForm` قبل اعتماد عقودها الخادمية ومصادرها.

## 6. الصلاحيات وحماية التدفق

كل انتقال بعد المصادقة يجب أن يعتمد على الدور الذي يعيده الخادم. لا يجوز قبول `portal` من المتصفح كبديل عن `ctx.user.role`. أي حفظ لملف أو مساحة عمل أو دعوة يجب أن يتحقق من ملكية المستخدم وصلاحيته في الإجراء الخادمي، مع اختبار supplier وauthority وregulator كل على حدة. يجب أن يبقى زر العودة إلى `/login` تنقلاً عادياً لا يبدأ OAuth تلقائياً.

## 7. المتطلبات غير المتاحة حالياً

| القدرة المقترحة في الموجز | القرار |
|---|---|
| OCR للسجل التجاري أو ملف الشركة | مؤجلة؛ تحتاج رفع ملفات وتخزيناً وخدمة OCR ومراجعة بشرية |
| Google/LinkedIn Workspace | مؤجلة؛ لا يوجد عقد أو موصل معتمد ضمن التدفق الحالي |
| MFA وBiometrics | مؤجلة؛ تعتمد على مزود مصادقة وخدمة جهاز فعلية |
| دعوات الفريق وتحديد أدوار جديدة | مؤجلة؛ تحتاج نماذج أعضاء وصلاحيات وworkflow تدقيق |
| شعار المؤسسة | مؤجل؛ يحتاج تخزين S3 وبيانات ملكية |
| الوضع الداكن الخاص بالمنظم | قرار تصميمي لاحق، وليس دليلاً على وجود طبقة أمان إضافية |

## 8. قرار التنفيذ المطلوب

المسار الآمن المقترح هو اعتماد **المرحلة A فقط** أولاً، لأنها توسع تجربة الدخول الحالية دون اختراع قدرات جديدة. بعد اختبارها، يُعتمد مسار المورد في المرحلة B. أما OCR وMFA وموفرو الدخول الخارجيون وتهيئة الفرق فتحتاج قرارات منفصلة ومراجعة تقنية وأمنية قبل إدراجها في المنتج.
