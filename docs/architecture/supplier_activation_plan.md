# SUPPLIER ACTIVATION PLAN

## PHASE 1 — Activation Plan Only

تستند هذه الخطة إلى فحص البوابة الموحدة الحالية داخل `/app`، و`Portal.tsx`، و`DashboardLayout`، وإجراءات الخادم الفعلية، ووثيقة هندسة المعلومات السابقة، واختبارات الصلاحيات الموجودة. لا تتضمن هذه المرحلة أي تعديل على الواجهة أو قاعدة البيانات أو إجراءات الخادم. الهدف هو تحديد ما يمكن تفعيله بأمان في نسخة MVP وما يجب إبقاؤه Future-ready.

## Existing active sections

توجد حالياً نواة تشغيلية للمورد داخل `Portal.tsx`، لكنها مجمعة في شاشة واحدة وليست مساحة عمل متعددة الأقسام. القدرات الفعلية المؤكدة هي: قراءة المستخدم والدور، قراءة الملف المؤسسي وحفظه، تصفح الصفقات المنشورة، إيداع عرض على صفقة منشورة، قراءة عروض المورد الحالي، واستخدام المساعد الذكي بصيغة إرشادية.

| القسم القابل للتفعيل | القدرة الفعلية | المصدر الحالي | الحالة الحالية |
|---|---|---|---|
| الرئيسية | ملخص مشتق من الملف والصفقات والعروض | `profile.get`, `tenders.published`, `bids.mine` | موجود جزئياً داخل الشاشة الموحدة |
| ملفي المؤسسي | قراءة وتحديث بيانات المؤسسة | `profile.get`, `profile.save` | موجود كمحرر داخل Dialog |
| الفرص المتاحة | قراءة الصفقات المنشورة | `tenders.published` | موجودة كقائمة داخل الشاشة الموحدة |
| تفاصيل الصفقة | قراءة حقول الصفقة المعادة | `tenders.get` | الإجراء موجود، لكن نطاقه الحالي يحتاج معالجة خادمية قبل جعله مشهداً مستقلاً |
| عروضي | متابعة عروض المستخدم الحالي | `bids.mine` | موجودة كقائمة مختصرة |
| تقديم عرض | إنشاء عرض جديد لصفقة منشورة | `bids.submit` | موجود داخل Dialog، مع تحقق القيمة والمقترح |
| المساعد الذكي | إرشاد وتلخيص عام | `assistant.ask` | موجود داخل بطاقة سياقية |

## Reusable components

يمكن إعادة استخدام `DashboardLayout` كإطار موحد للمصادقة والرأس والقائمة الجانبية وتسجيل الخروج، مع الحاجة إلى إضافة مساحة Sidebar خاصة بالمورد بدلاً من تمرير عناصر عامة ثابتة. كما يمكن إعادة استخدام `AIChatBox` داخل مكوّن `SupplierAssistantCard`، ومكونات Shadcn/UI مثل `Card`, `Badge`, `Button`, `Dialog`, `Input`, `Textarea` و`Progress` لبناء الحالات المؤسسية RTL.

| المكوّن القابل لإعادة الاستخدام | دوره في التفعيل |
|---|---|
| `DashboardLayout` | الإطار العام المحمي داخل `/app` |
| `AIChatBox` | واجهة المساعد الإرشادي دون تغيير عقد `assistant.ask` |
| `ProfileEditor` الحالي | أساس صفحة الملف بعد تحويله من Dialog ضيق إلى مشهد واضح عند الحاجة |
| `StatusBadge` | ترجمة حالات الصفقات والعروض الفعلية فقط |
| `TenderForm` ونافذة تقديم العرض الحالية | مصدر سلوك الحقول والتحقق، لا تُنقل كما هي إذا كانت التجربة الجديدة تحتاج Panel أوسع |
| مكونات Shadcn/UI | حالات التحميل والفراغ والخطأ والنجاح والنماذج |

## Missing routes

المسار الوحيد المسجل حالياً للبوابة هو `/app`. لا توجد مسارات عميقة خاصة بالمورد في `App.tsx`. لذلك يكون التنفيذ الآمن الأولي داخل `/app` باستخدام حالة قسم داخلية أو query parameter مثل `/app?section=profile`، مع إبقاء `/app` الافتراضي متوافقاً مع الجلسات الحالية.

| المشهد المقترح | المسار الانتقالي الآمن | ملاحظة |
|---|---|---|
| الرئيسية | `/app` أو `/app?section=home` | نقطة الدخول الافتراضية |
| ملفي المؤسسي | `/app?section=profile` | يعتمد على `profile.get/save` |
| الفرص المتاحة | `/app?section=tenders` | يعتمد على `tenders.published` |
| تفاصيل الصفقة | حالة داخلية أو `/app?section=tender&id=:id` | لا يعتمد كمسار قابل للنشر قبل تأمين نطاق `tenders.get` خادمياً |
| عروضي | `/app?section=bids` | يعتمد على `bids.mine` |
| المساعد الذكي | `/app?section=assistant` | يعتمد على `assistant.ask` |

## Required new components

المرحلة التنفيذية اللاحقة تحتاج إلى `SupplierWorkspace` لتنسيق القسم النشط، و`SupplierSidebar` للتنقل، و`SupplierHome` للملخص، و`SupplierKpiStrip` للمؤشرات المشتقة، و`PublishedTenderList` و`TenderOpportunityCard` للفرص، و`TenderDetailPanel` للتفاصيل، و`BidSubmissionPanel` للتقديم، و`SupplierBidList` و`BidStatusBadge` للعروض، و`SupplierProfilePage` أو `SupplierProfilePanel` للملف، و`SupplierAssistantPanel` للمساعد، و`FutureReadyPanel` للعناصر غير المفعلة إذا تقرر عرضها في القائمة.

لا ينبغي إنشاء هذه المكونات في PHASE 1. كما لا ينبغي أن تحمل أسماء أو مؤشرات توحي بوجود مطابقة أو إشعارات أو مستندات ما لم تُضف نماذج واستعلامات حقيقية في مرحلة مستقلة.

## Safe data sources

| مصدر البيانات | نطاق القراءة الآمن | التحويلات المسموحة في الواجهة |
|---|---|---|
| `profile.get` | ملف المستخدم الحالي وفق `ctx.user.id` | عرض الحقول الموجودة وحساب نسبة الاكتمال المرسلة أو المشتقة من الحقول الأربعة |
| `profile.save` | تحديث ملف المستخدم الحالي | حفظ `organizationName`, `registrationNumber`, `phone`, `address`, و`completion` فقط |
| `tenders.published` | صفقات حالتها `published` | عدد، ترتيب، فلترة محلية بسيطة، وعرض الحقول المعادة |
| `tenders.get` | تفاصيل صفقة بالمعرف | يجب ألا يُعرض للمورد قبل إضافة تحقق خادمي يضمن عدم كشف صفقة غير منشورة أو بيانات داخلية |
| `bids.mine` | عروض مرتبطة بـ`ctx.user.id` | عدّ وترتيب وترجمة الحالات الفعلية |
| `bids.submit` | عرض جديد لصفقة منشورة | تحقق القيمة الموجبة والمقترح الذي لا يقل عن 20 حرفاً |
| `assistant.ask` | سؤال إرشادي محمي للمستخدم الحالي | شرح وتلخيص واقتراح خطوة عامة دون قرار أو mutation تعاقدي |

## Future-ready sections

تُبقى الأقسام التالية خارج التفعيل الوظيفي في هذه الدورة: الفرص المطابقة لي، المستندات، الإشعارات، والإعدادات. لا توجد حالياً نماذج أو استعلامات أو mutations حقيقية لها. إذا لزم إظهارها ضمن خارطة التنقل، فتظهر في نهاية القائمة بوسم «قريباً» أو داخل `FutureReadyPanel` يوضح أن البيانات والاعتماديات غير متاحة بعد. لا تعرض هذه العناصر counters أو جداول وهمية أو تنبيهات أو صفحات تبدو مكتملة.

كما لا يُفعل تعديل العرض أو سحبه، ورفع الوثائق، ونسب الملاءمة، وتحليل عروض المنافسين، وقرارات الفوز، لأنها غير مدعومة بإجراءات أو بيانات مناسبة للمورد.

## Permissions

المورد يستطيع قراءة ملفه فقط عبر `profile.get`، وتحديث ملفه فقط عبر `profile.save`، وقراءة عروضه فقط عبر `bids.mine`، وتقديم عرض فقط عبر `bids.submit` لصفقة منشورة. لا يستطيع إنشاء أو نشر أو إغلاق صفقة، أو قراءة عروض صفقة مملوكة لجهة متعاقدة، أو تقييم عرض، أو اتخاذ قرار إسناد.

الحماية الحالية تغطي منع المورد من `tenders.mine`, `tenders.create`, و`bids.forTender`، كما تمنع الأدوار غير المناسبة من عمليات المورد. لكنها لا تغطي بعد اختباراً صريحاً لمورد يطلب `tenders.get` لصفقة غير منشورة أو يغير معرفات الكيانات في مشهد التفاصيل. لذلك يجب اعتبار هذا بند تحقق خادمي سابقاً لتفعيل تفاصيل الصفقة كمسار مستقل.

## Risks

الخطر الأهم هو أن `tenders.get` معرف حالياً كإجراء عام ويعيد الصفقة بالمعرف دون فحص حالة النشر أو الدور. هذا لا يعني أن البيانات الداخلية تظهر الآن في قائمة `tenders.published`، لكنه يجعل أي شاشة تفاصيل تعتمد عليه بحاجة إلى حارس خادمي قبل التفعيل. الحل الآمن هو قصر التفاصيل العامة على الصفقة المنشورة أو إضافة عقد خادمي صريح يفرض هذا القيد، ثم اختبار صفقة غير منشورة وتغيير المعرف يدوياً.

الخطر الثاني هو أن الشاشة الحالية تجمع عدة وظائف داخل `Portal.tsx` وتستخدم مسارات `/app` عامة. يجب فصل فرع المورد تدريجياً دون تعديل منطق authority أو regulator، مع الحفاظ على `/app` كمدخل موحد. والخطر الثالث هو احتمال عرض حالات عروض إضافية غير معروفة؛ لذلك يقتصر العرض على الحالات الفعلية `submitted`, `under_review`, `accepted`, و`rejected`، مع تسمية احتياطية صادقة لأي قيمة جديدة بدلاً من ترجمة مخترعة.

## Recommended phased execution

| المرحلة | النطاق المقترح | شرط الانتقال |
|---|---|---|
| PHASE 2 | Shell وSidebar والتنقل داخل `/app` | اعتماد هذه الخطة وعدم تغيير عقد الخادم |
| PHASE 3 | الرئيسية والملف المؤسسي | حالات loading/empty/error واختبارات الملف |
| PHASE 4 | الفرص وتفاصيل الصفقة | تأمين `tenders.get` خادمياً قبل إظهار التفاصيل |
| PHASE 5 | عروضي وتقديم العرض | اختبارات ملكية المورد والتحقق من الصفقات المنشورة |
| PHASE 6 | المساعد وFuture-ready | إبقاء المساعد إرشادياً والعناصر غير المدعومة معطلة |
| PHASE 7 | التحقق الشامل | اختبار الأدوار وتغيير المعرفات والتوافق مع `/app` |

> لا يبدأ تنفيذ الواجهة في PHASE 1. هذه الوثيقة هي خطة تفعيل فقط، وأي انتقال إلى PHASE 2 يحتاج اعتماداً صريحاً للنطاق والمسارات والمخاطر المذكورة أعلاه.
