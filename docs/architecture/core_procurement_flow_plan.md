# CORE PROCUREMENT FLOW PLAN

## 1. نطاق الخطة

تستهدف هذه الخطة إغلاق المسار الأساسي الفعلي من إنشاء صفقة لدى المصلحة المتعاقدة إلى إرسال عرض نهائي من المتعامل الاقتصادي قبل الموعد النهائي. لا تشمل الخطة الذكاء الاصطناعي أو التحليلات أو تنفيذ العقد، ولا تفترض وجود Django/DRF أو Next.js في المستودع الحالي؛ الفحص الفعلي يثبت أن المشروع مبني حالياً على React/Vite في الواجهة وExpress/tRPC في الخادم وDrizzle ORM مع MySQL/TiDB.

> القاعدة الحاكمة: لا يُعد أي تدفق مكتملاً لمجرد وجود واجهة له؛ يجب أن يكون العقد الخادمي، وتحقق الملكية والصلاحية، والتحقق الزمني، وسجل التدقيق، والاختبار متوافرة أو موثقة كفجوة.

## 2. النموذج/النماذج المستخدمة حالياً والمطلوبة

| المجال | الموجود فعلياً | المطلوب لإغلاق المسار | الحكم الحالي |
|---|---|---|---|
| المستخدم والملف | `users` و`profiles` | لا تغيير جوهري للمسار، مع تثبيت إدارة الأدوار خارج اختيار المستخدم الذاتي | جزئي؛ `auth.setRole` يسمح للمستخدم ذي الدور `user` باختيار `supplier` أو `authority` أو `regulator` |
| الصفقة | `tenders` | الحقول الحالية تكفي للبيانات الأساسية والميزانية والموعد، لكن يجب إضافة علاقة وثائق وفرض تحقق نشر مستقل | موجود جزئياً |
| العرض | `bids` | إضافة مسودة عرض، تحديث مملوك للمورد، وثم إرسال نهائي منفصل، مع منع التعديل بعد الأجل | غير كافٍ؛ الموجود هو `bids.submit` النهائي فقط |
| وثائق الصفقة | لا يوجد جدول مجال أو endpoint | جدول metadata مرتبط بالصفقة وعقد رفع/تنزيل موقّع ومتحقق الصلاحية | مفقود |
| وثائق العرض | لا يوجد جدول مجال أو endpoint | جدول metadata مرتبط بالعرض، ورفع قبل الإرسال أو وفق سياسة واضحة، وتنزيل محمي | مفقود |
| سجل التدقيق | `auditLogs` يحوي actor/action/entity/result/metadata/createdAt | تسجيل عمليات إنشاء وتحديث ونشر ورفع وتنزيل وحفظ مسودة وإرسال نهائي ورفض زمني، ويفضل `requestId` إذا كان متاحاً | موجود جزئياً |
| التخزين | `storagePut` و`storageGet` و`storageGetSignedUrl` | ربط التخزين بكيانات مجال وقواعد ملكية وتنزيل حسب الدور | primitives فقط، بلا حماية مجال |

## 3. حالات Tender الحالية والمقترحة

الحالات الفعلية في schema هي: `draft` و`published` و`closed` و`evaluation` و`awarded` و`cancelled`. لا يُضاف اسم حالة جديد في هذه الخطة. التسمية المنطقية المقابلة للمراحل المطلوبة هي:

| الحالة الحالية | المعنى في المسار | ملاحظة تنفيذية |
|---|---|---|
| `draft` | صفقة قابلة للإعداد من مالكها | يمكن تحديث الحقول والوثائق قبل النشر |
| `published` | صفقة منشورة وقابلة للعرض العام وتقديم العروض قبل الأجل | لا يسمح بتعديل جوهري عبر `tenders.update` الحالي |
| `closed` | استقبال مغلق والصفقة جاهزة للتقييم | الانتقال الحالي يدوي عبر `tenders.close` |
| `evaluation` | قيد تقييم العروض | الانتقال الحالي عبر `tenders.startEvaluation` |
| `awarded` | أُسندت الصفقة | عبر `awards.decide` بعد قبول عرض |
| `cancelled` | أُلغيت الصفقة | عبر `awards.decide` من حالة التقييم |

### الانتقالات المسموح بها حالياً والمطلوبة

| من | إلى | الإجراء | صاحب الصلاحية | الوضع |
|---|---|---|---|---|
| لا توجد | `draft` | `tenders.create` | `authority` أو `admin` | موجود، لكنه يتطلب كل payload في أول حفظ |
| `draft` | `draft` | `tenders.update` | مالك الصفقة أو `admin` | موجود، ويجب أن يبقى مقيداً بالملكية |
| `draft` | `published` | `tenders.publish` | مالك الصفقة أو `admin` | موجود، ويحتاج تحقق نشر مستقل للحقول والوثائق إن أصبحت الوثائق إلزامية |
| `published` | `closed` | `tenders.close` | مالك الصفقة أو `admin` | موجود كإجراء يدوي؛ يجب ألا يعتمد على وقت العميل |
| `closed` | `evaluation` | `tenders.startEvaluation` | مالك الصفقة أو `admin` | موجود |
| `evaluation` | `awarded`/`cancelled` | `awards.decide` | مالك الصفقة أو `admin` | موجود مع تحقق العرض الفائز |
| `published` | `draft` أو تحديث جوهري | غير مسموح | لا أحد عبر العقد الحالي | يجب الحفاظ عليه، وعدم اختراع versioning غير مدعوم |

## 4. حالات Bid الحالية والمقترحة

الحالات الفعلية في schema هي `submitted` و`under_review` و`accepted` و`rejected`. لا توجد حالتا `draft` أو `sealed` أو `opened` في البنية الحالية، ولذلك لا يمكن ادعاء دعم حفظ مسودة العرض أو الفتح القانوني دون migration وتغيير عقد.

| الحالة | الوضع الحالي | المطلوب |
|---|---|---|
| `draft` | غير موجود | إضافة حالة فقط إذا اعتمدت migration صريحة، مع إجراءات create/update مملوكة للمورد |
| `submitted` | موجود وينشأ مباشرة من `bids.submit` | تحويله إلى الإرسال النهائي فقط بعد اكتمال البيانات والوثائق وقبل وقت الخادم |
| `under_review` | موجود | يبقى انتقالاً خادمياً من مرحلة التقييم |
| `accepted` | موجود | يبقى شرطاً قبل الإسناد |
| `rejected` | موجود | يبقى نتيجة تقييم قابلة للتدقيق |

إذا كان المطلوب الاحتفاظ بمسودة عرض حقيقية، فالمسار المقترح هو `draft -> submitted -> under_review -> accepted/rejected`. أما إضافة `sealed` أو `opened` فتتطلب قراراً مستقلاً ونموذجاً قانونياً وتقنياً لمحضر الفتح، وهي خارج الإغلاق الأدنى لهذا المسار ما لم يعتمدها صاحب المنتج صراحة.

## 5. endpoints الموجودة والمطلوبة

| النطاق | الإجراء الحالي | المطلوب في الإغلاق | الصلاحيات |
|---|---|---|---|
| إنشاء صفقة | `tenders.create` | الإبقاء مع تحقق خادمي للحقول والموعد | authority/admin |
| تحديث مسودة | `tenders.update` | الإبقاء، مع منع أي تحديث خارج `draft` وتثبيت الملكية | مالك authority/admin |
| نشر | `tenders.publish` | إضافة تحقق مستقل من اكتمال البيانات والموعد والوثائق المطلوبة | مالك authority/admin |
| عرض المنشور | `tenders.published` | الإبقاء، ويجب أن يعتمد على حالة `published` ووقت الخادم | public، مع عدم كشف مسودات |
| تفاصيل صفقة | `tenders.get` | تقييد التفاصيل والوثائق حسب حالة الصفقة وسياسة الكشف | public أو protected حسب المحتوى |
| قائمة المورد | `bids.mine` | الإبقاء مع قصر النتائج على `supplierId = ctx.user.id` | supplier/admin |
| بدء عرض | غير موجود؛ الواجهة تستدعي النهائي مباشرة | `bids.createDraft` أو عقد مكافئ | supplier/admin مع supplierId من الجلسة |
| تحديث مسودة | غير موجود | `bids.updateDraft` | مالك العرض فقط، وما دامت الحالة `draft` وقبل الأجل |
| رفع وثيقة صفقة | غير موجود | `tenderDocuments.upload` أو upload intent محمي | authority لصفقته فقط |
| تنزيل وثيقة صفقة | غير موجود | `tenderDocuments.download` مع تحقق حالة/كشف | supplier للصفقة المنشورة، authority المالك، regulator وفق سياسة |
| رفع وثيقة عرض | غير موجود | `bidDocuments.upload` مع تحقق ملكية ومسودة | supplier المالك فقط |
| تنزيل وثيقة عرض | غير موجود | `bidDocuments.download` مع منع الكشف قبل المرحلة المسموحة | supplier المالك، authority في مرحلة مسموحة، regulator وفق سياسة |
| إرسال نهائي | `bids.submit` | فصل عقد الإرسال النهائي أو توسيعه ليقبل draft ويغيرها إلى submitted | supplier المالك فقط، قبل وقت الخادم |
| التدقيق | `logAudit` داخلي | توسيع التسجيل لكل العمليات الحساسة مع نتيجة الفشل حيث يمكن | الخادم فقط |

## 6. خطة الوثائق

يوفر المشروع primitives للتخزين الموقّع في `server/storage.ts`، لكنه لا يملك metadata أو علاقات أو authorization على مستوى الصفقة والعرض. لذلك لا يكفي استدعاء `storagePut` من الواجهة. يلزم إنشاء جدولين أو نموذج موحد موثق بوضوح، يتضمن على الأقل: المعرف، نوع الكيان، معرف الكيان، المالك أو صاحب الصلة، اسم الملف، نوع MIME، الحجم، مفتاح التخزين، تاريخ الإنشاء، وحالة الحذف إن كانت مطلوبة. يجب ألا تُحفظ bytes داخل قاعدة البيانات.

الرفع يجب أن يمر عبر endpoint خادمي ينشئ intent أو ينفذ الرفع، ثم يسجل metadata بعد نجاحه. التنزيل يجب أن يعيد رابطاً موقّعاً قصير العمر بعد تحقق الصلاحية على الخادم؛ ولا يجوز كشف مفتاح التخزين الخام للواجهة.

## 8. الاختبارات المطلوبة

ينبغي تغطية الحالات التالية باختبارات خادمية حقيقية أو mocks مضبوطة للعقود، مع عدم اعتبار mock data دليلاً على صلاحية الإنتاج: إنشاء مسودة مملوكة، رفض إنشاء أو تحديث من دور غير مسموح، منع تحديث صفقة منشورة، رفض نشر صفقة ناقصة، رؤية المورد للصفقات المنشورة غير المنتهية فقط، منع رؤية مسودات الصفقة، إنشاء مسودة عرض مملوكة، منع تعديل مسودة مورد آخر، رفع وثيقة بملكية صحيحة، رفض تنزيل وثيقة غير مصرح بها، حفظ الوثيقة مع metadata، إرسال نهائي قبل الأجل، رفض الإرسال بعد الأجل وفق وقت الخادم، رفض التعديل بعد الأجل، وعدم حذف بيانات العرض عند انتقال الحالة.

ويجب إضافة اختبار تكاملي لمسار كامل، واختبار متصفح أو E2E لمسار authority ثم supplier، واختبارات RTL/mobile وحالات loading/empty/error/success. كما يجب تشغيل typecheck وlint وunit/integration tests وbuild، مع توثيق أي فشل سابق غير مرتبط مباشرة بالميزة.

## 9. التعارضات الحالية مع المطلوب

| المطلوب | التعارض الفعلي |
|---|---|
| Django/DRF + Next.js | المستودع الحالي ليس Django/Next.js؛ هو React/Vite + Express/tRPC + Drizzle/MySQL/TiDB |
| إضافة الوثائق | لا توجد جداول أو endpoints أو واجهات مجال للوثائق |
| حفظ مسودة العرض | `bids` لا يملك `draft`، والواجهة تستدعي `bids.submit` النهائي مباشرة |
| تعديل مسودة العرض | لا يوجد `bids.updateDraft`، والواجهة تصرح بعدم دعم التعديل أو الاستبدال |
| إرسال نهائي منفصل | لا يوجد فصل بين إنشاء/حفظ المسودة والإرسال النهائي |
| منع تعديل العرض بعد الأجل | منع الإرسال بعد الأجل موجود في `bids.submit`، لكن لا يوجد أصلاً عقد تعديل مسودة لاختباره |
| الوثائق المسموح بها | storage helpers لا تفرض policy حسب tender/bid/role |
| سجل تدقيق غني | موجود للعمليات الأساسية، لكنه لا يملك requestId ولا يسجل كل محاولات الفشل والوثائق |
| اعتماد وقت الخادم | المقارنة الخادمية في `bids.submit` موجودة؛ الواجهة تستخدم `Date.now()` للعرض فقط، ولا يجوز استخدامها كحكم أمني |

## 10. تصنيف MVP قبل التنفيذ

| المجال | التصنيف الحالي |
|---|---|
| إنشاء الصفقة والمسودة والنشر | `IMPLEMENTED_NOT_VERIFIED`؛ العقد موجود مع اختبارات mocked، لكن النشر لا يتحقق من وثائق لأنها غير موجودة |
| رؤية الصفقات المنشورة والبحث والتصفية | `IMPLEMENTED_AND_VERIFIED` بالنسبة للبيانات الحالية؛ التصفية محلية بعد جلب القائمة |
| تفاصيل الصفقة | `PARTIAL`؛ `tenders.get` عام، ولا توجد شاشة تفاصيل مستقلة أو policy وثائق |
| إضافة وثائق الصفقة | `MISSING` |
| بدء مسودة العرض وتحديثها | `MISSING` |
| رفع وثائق العرض | `MISSING` |
| الإرسال النهائي قبل الأجل | `PARTIAL`؛ الإرسال النهائي موجود مع تحقق خادمي للموعد لكنه ينشئ العرض مباشرة |
| منع الإرسال بعد الأجل | `IMPLEMENTED_AND_VERIFIED` في عقد `bids.submit` واختبار workflow |
| منع تعديل العرض بعد الأجل | `MISSING` كعقد مستقل، لأن التعديل غير موجود |
| قصر بيانات المورد على ملكيته | `IMPLEMENTED_NOT_VERIFIED`؛ الاستعلامات مقيدة بالمعرف، لكن تغطية السيناريوهات متعددة المستخدمين محدودة |
| التدقيق للعمليات الحساسة | `PARTIAL` |
| حالات الواجهة | `IMPLEMENTED_NOT_VERIFIED`؛ loading/empty/error/success موجودة في أجزاء رئيسية، دون تغطية المسار الجديد للوثائق والمسودة |

## 11. قرار التنفيذ المقترح

ينبغي تنفيذ المسار على مرحلتين داخل نفس نطاق Core Procurement Flow. المرحلة الأولى تضيف الوثائق ومسودة العرض وعقد الإرسال النهائي، مع migration وعلاقات الملكية واختبارات الخادم. المرحلة الثانية توصل الواجهتين وتضيف E2E وRTL/mobile. لا ينبغي بدء UI النهائي قبل اعتماد قرارين: هل وثائق الصفقة ووثائق العرض إلزامية للنشر والإرسال في MVP، وهل إضافة حالة `draft` للعرض مقبولة ضمن enum الحالي أم يجب استخدام كيان مسودة منفصل.

## 12. الخلاصة

المشروع يملك أساساً صالحاً لمسار مبسط: صفقة draft ثم published، قائمة صفقات منشورة، وعرض نهائي مع deadline خادمي. لكنه لا يحقق بعد المسار المطلوب كاملاً بسبب غياب الوثائق، غياب مسودة العرض، غياب التعديل المملوك، وعدم الفصل بين الحفظ والإرسال النهائي. لذلك لا يوصى باعتبار Core Procurement Flow مغلقاً قبل اعتماد هذه القرارات وتنفيذ migration والعقود والاختبارات المذكورة.

> هذه الوثيقة خطة ما قبل التنفيذ فقط. لم تُجرَ فيها أي تعديلات وظيفية على الكود، ولا تتضمن بيانات تجريبية أو ادعاء اكتمال للقدرات غير الموجودة.
