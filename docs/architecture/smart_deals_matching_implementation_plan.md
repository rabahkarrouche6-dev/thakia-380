# SMART DEALS MATCHING IMPLEMENTATION PLAN

## 1. Executive Scope

الملف المرفق يفترض Django Templates وPostgreSQL، بينما الفحص الفعلي للمشروع يثبت أن منصة **صفقات ذكية** مبنية على React 19 وVite في الواجهة، وExpress/tRPC 11 وDrizzle مع MySQL/TiDB في الخادم. لذلك لن تتم إضافة Django app أو DRF endpoint أو migrations جديدة لمجرد مطابقة الافتراض الوارد في الملف. سيُحافظ التنفيذ على convention الحالي، ويُوسّع محرك المطابقة الموجود في `server/tenderMatching.ts` فقط إذا دعمت البيانات الحالية ذلك.

## 2. ما هو موجود وقابل لإعادة الاستخدام

| المجال | الموجود فعلياً | قرار الخطة |
|---|---|---|
| الصفقات | `Tender`، حالات، `tenders.published`، وقت نشر وdeadline | إعادة الاستخدام مع تصفية الخادم قبل التوصية |
| المورد | `Profile` المرتبط بالمستخدم، خصوصاً اسم المؤسسة والعنوان وحالة الاكتمال | إعادة الاستخدام دون اختراع ملف تجاري جديد في هذه المرحلة |
| الواجهة | `SupplierWorkspace` ومسار `/app?section=home` وقائمة الصفقات والتفاصيل | دمج بطاقة التوصيات داخل الصفحة الحالية |
| العقد الخادمي | tRPC محمي بالدور وملكية الحساب | إضافة/توسيع procedure متوافق بدلاً من REST أو DRF |
| المطابقة الحالية | `server/tenderMatching.ts` مع تصفية زمنية، تطبيع، scoring وتفسير | اعتباره نواة MVP الحالية، ثم تحسينه دون ادعاء ML |
| التخزين | Drizzle/MySQL أو TiDB، وS3 للوثائق | عدم تخزين محتوى الوثائق في نتيجة المطابقة |
| التدقيق والقياس | Audit Trail وProduct Analytics منفصلان | تسجيل أحداث التفاعل فقط عبر طبقة observability القائمة |
| الاختبارات | Vitest وعقود صلاحيات وتدفق المورد | إضافة اختبارات pure للطبقات الجديدة واختبارات integration للعقد |

## 3. ما هو غير موجود

لا توجد بنية Django أو `manage.py` أو `pytest.ini` أو DRF في المشروع الحالي. كما لا توجد حقول منظمة مؤكدة للرمز التجاري، الفئات الثانوية، النشاطات، الولايات المغطاة، درجة التأهيل، الخبرات السابقة، الوثائق الإلزامية المنتهية، أو blacklist للمورد. لا توجد حالياً سياسة موثقة تسمح بتحويل غياب هذه البيانات إلى سبب إقصاء.

لا توجد كذلك بنية cache durable أو job queue أو Celery/Redis لمحرك المطابقة. لذلك لا يجوز إضافة persistence/cache أو refresh background كحل شكلي قبل توثيق schema واحتياج الأداء وقياسه.

## 4. الحقول التي يمكن استخدامها مباشرة

يمكن استخدام الحقول الحقيقية الآتية فقط:

| الكيان | الحقول المتاحة للاستخدام |
|---|---|
| Tender | `id`, `reference`, `title`, `description`, `category`, `location`, `deadline`, `status`, `publishedAt`, `authorityId` |
| Supplier profile | `organizationName`, `address`, `completion` والهوية الخادمية للحساب |
| Business context | وقت الخادم الحالي وحالة الصفقة المنشورة |

يُستخدم `organizationName` و`address` كإشارات نصية إرشادية محدودة، وليس كبديل عن رمز نشاط أو تغطية جغرافية منظمة.

## 5. الحقول الناقصة

لا يمكن تنفيذ قواعد إقصاء تخص qualification grade أو نوع المؤسسة أو الوثائق الإلزامية أو الخبرة أو قوائم الحظر أو `covered_wilayas` لأنها غير موجودة كحقول مؤكدة أو سياسة تشغيلية في المخطط الحالي. نقص هذه البيانات سيخفض جودة التفسير أو يظهر كفجوة معلومات، لكنه لن يؤدي إلى إقصاء المورد تلقائياً.

## 6. تعارضات النماذج والقرار بشأن Models

يوجد تعارض بين نموذج الملف المرفق ونموذج المشروع الفعلي: الملف يقترح `SupplierMatchingProfile` و`TenderMatchCache`، لكن المشروع الحالي يملك `Profile` عامة ولا يملك persistence للمطابقات. لن يُنشأ Model جديد في MVP الحالي؛ لأن ذلك يتطلب migration وتحديد مالك تجاري للبيانات وسياسة تحديث واحتفاظ.

لا توجد حاجة إلى model للنتائج المخزنة في النسخة الحالية. ستظل النتائج مشتقة عند الطلب من الصفقة المنشورة والملف الحالي. يمكن اقتراح `SupplierMatchingProfile` و`TenderMatchCache` في V1 فقط بعد اعتماد الحقول والسياسات وقياس الحاجة.

## 7. الحاجة إلى Service Layer

نعم، يجب إبقاء المنطق خارج router وواجهة React. الطبقات العملية في هذا المشروع ستكون دوال pure وخدمات TypeScript داخل `server/tenderMatching.ts`، مع فصل منطقي بين candidate generation وeligibility وscoring وsemantic keyword matching وexplanation. لا تُستخدم LLM أو خدمة خارجية داخل request path.

## 8. Candidate Generation وEligibility المقترحان

يجب أن يبدأ المرشحون من `tenders.published` أو query خادمي مكافئ، مع استبعاد أي صفقة غير منشورة أو منتهية وفق وقت الخادم. لا تُعرض الصفقة الملغاة أو المنتهية حتى لو احتوت على تشابه نصي.

في غياب قواعد أهلية معلنة، تكون النتيجة الزمنية/الحالية هي البوابة الوحيدة القابلة للإثبات. لا تُنشأ قاعدة قانونية جديدة من category mismatch أو نقص الملف. إذا أضيفت لاحقاً قاعدة صريحة إلى schema، يجب أن تعيد `EligibilityResult` أسباباً قابلة للتدقيق ونسخة قواعد واضحة.

## 9. Scoring MVP المقترح

النواة الحالية تستخدم category، text/semantic، location، وprofile readiness. يمكن الاحتفاظ بها كنسخة MVP تفسيرية مع تعريف الأوزان في ثابت واحد والتحقق آلياً من مجموعها. لا يجوز ادعاء أن التنفيذ TF-IDF أو embeddings إذا كان فعلياً keyword overlap وتطبيعاً عربياً.

أما documents وexperience وqualification فلا تدخل في الدرجة الحالية لأنها غير متاحة كبيانات منظمة. إذا احتاجت المواصفة أوزاناً سداسية كاملة، فسيُعاد توزيع الأوزان على الإشارات المتاحة بشكل موحد ومُوثق، مع خفض confidence وإظهار أن البيانات جزئية، لا إضافة درجات وهمية.

## 10. Explanation وRelevance Bands

كل نتيجة يجب أن تعيد درجة بين 0 و100، تصنيفاً قابلاً للتعديل، وسببين أو ثلاثة مشتقة من الحقول الفعلية، مع فجوات لا تتجاوز ثلاثة. يجب أن يظهر التنويه التالي في واجهة المورد:

> هذه المطابقة أداة مساعدة مبنية على البيانات المتوفرة في ملفك، ولا تغني عن قراءة دفتر الشروط والتحقق من الشروط الرسمية.

ممنوع عرض احتمال الفوز أو الأهلية القانونية النهائية أو مقارنة المنافسين. يجب الفصل بين `LOW_FIT` و`NOT_ELIGIBLE`، وعدم استخدام `NOT_ELIGIBLE` إلا عندما تكون قاعدة الإقصاء مثبتة فعلياً.

## 11. Persistence / Cache / Refresh

لا persistence ولا cache في MVP الحالي. سيُعاد الحساب عند طلب المورد مع حد داخلي للنتائج، وتُراجع حالة الصفقة قبل العرض. إذا أثبتت المقاييس لاحقاً تكلفة غير مناسبة، تكون الخطوة التالية cache versioned مع algorithm version وexpiry وقيود unique/index، بعد migration موثقة واختبارات freshness.

## 12. API أو واجهة المشروع

المسار الصحيح هو tRPC الموجود، وليس `/api/v1/recommendations` المقترح في الملف. العقد المقترح هو procedure محمية للمورد، لا تستقبل `supplierId` من العميل، وتقرأ المورد من session server context. يمكن قبول `limit` مستقبلاً بحد أعلى صغير بعد الحاجة، مع رفض القيم السالبة أو الضخمة وعدم الوثوق بأي score قادم من العميل.

## 13. Portal Integration

تُدمج بطاقة «الصفقات الأنسب لنشاطك» داخل `SupplierWorkspace` في الصفحة الرئيسية. تعرض البطاقة عنوان الصفقة، المرجع، التصنيف، الدرجة، سبباً أو سببين، فجوة عند وجودها، وزر تفاصيل يستخدم مسار الفرص المنشورة الحالي. يجب توفير حالة profile incomplete، no recommendations، error، no permission، وexpired recommendation دون كسر الصفحة.

## 14. الملفات المتوقع تغييرها

| النوع | الملفات |
|---|---|
| خادم | `server/tenderMatching.ts`، `server/routers.ts`، وربما `server/db.ts` فقط إذا احتاجت candidate query محسنة |
| واجهة | `client/src/pages/SupplierWorkspace.tsx`، وربما مكوّن بطاقة مشترك إذا ثبتت الحاجة |
| اختبارات | `server/tenderMatching.test.ts`، اختبار عقد الإجراء، واختبار view contract للمورد |
| توثيق | هذا الملف ثم `smart_deals_tender_matching_implementation_report.md` |
| Schema/migration | لا تغيير في MVP الحالي ما لم يكشف التدقيق حقلاً فعلياً لازماً |

## 15. الاختبارات المطلوبة

يجب اختبار استبعاد الصفقات غير المنشورة والمنتهية، حماية المورد من نتائج مورد آخر، رفض الوصول غير المصادق، ثبات الدرجة، المجال 0–100، تفسير الأسباب من بيانات حقيقية، الحد الأقصى للأسباب والفجوات، تطبيع العربية والمصطلحات المختلطة، عدم الإقصاء عند غياب بيانات اختيارية، وعدم كشف بيانات المنافسين. يجب أن تبقى اختبارات core procurement وRBAC وdocument security وobservability ناجحة.

## 16. مخاطر التنفيذ

الخطر الرئيسي هو محدودية profile الحالي؛ لا يمكن لمحرك يعتمد على اسم المؤسسة والعنوان أن يثبت تطابقاً تجارياً عميقاً. الخطر الثاني هو التباس الدرجة لدى المستخدم؛ لذلك يجب وصفها بأنها إرشادية وعدم استعمالها في تقييم أو إرساء. الخطر الثالث هو توسع النطاق إلى schema أو ML أو cache قبل وجود labels وأداء مقاس. أخيراً، يجب استمرار حماية server-side وعدم اعتبار إخفاء البطاقة أو الزر حماية.

## 17. القرار التنفيذي

المطلوب التالي هو تنفيذ **MVP محدوداً داخل البنية الحالية**، لا إعادة بناء Django ولا إنشاء نماذج أو APIs غير متوافقة. بعد التنفيذ يجب إصدار تقرير `SMART DEALS TENDER MATCHING IMPLEMENTATION REPORT` يميز بوضوح بين `IMPLEMENTED` و`PARTIALLY_IMPLEMENTED`، ويذكر الحقول الناقصة، الاختبارات، والقيود. لا يُعتبر المحرك مكتملًا بموجب المواصفة الكاملة إلا بعد إضافة بيانات منظمة للأنشطة والجغرافيا والوثائق والخبرة وسياسات eligibility قابلة للمراجعة.
