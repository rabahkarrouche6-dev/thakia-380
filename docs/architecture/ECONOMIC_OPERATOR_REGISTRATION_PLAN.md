# ECONOMIC OPERATOR REGISTRATION — GAP & IMPLEMENTATION PLAN

> **تنبيه مهني:** هذه الوثيقة تحليل هندسي أولي وليست رأياً قانونياً أو اعتماداً للامتثال. يجب مراجعة النصوص والحقول والإقرارات النهائية من مستشار قانوني جزائري مختص قبل استخدامها مع بيانات حقيقية.

## 1. خلاصة القرار الهندسي

المواصفات المرفقة تصف Django/DRF وNext.js، بينما المشروع الحالي مبني فعلياً على React 19 وVite وtRPC 11 وExpress وDrizzle مع Manus OAuth. لذلك لا يُنصح بإعادة كتابة المنصة إلى Django/Next.js من أجل هذا التدفق. المسار الآمن هو إضافة شاشة تسجيل/استكمال ملف للمتعامل الاقتصادي فوق البنية الحالية، مع إبقاء المصادقة وتعيين الدور خادميين عبر OAuth وtRPC.

المرحلة الأولى القابلة للتنفيذ هي **استكمال ملف المتعامل الاقتصادي بعد تسجيل الدخول**. أما إنشاء حساب محلي بالبريد وكلمة المرور، وتخزين وثائق الهوية والبيانات البنكية الحساسة، والتحقق القانوني الخارجي من NIF/NIS/RC، فتتطلب قرارات بنيوية ومصادر تحقق واعتمادات لا يوفرها المشروع الحالي تلقائياً، ولذلك لا ينبغي اختلاقها أو محاكاتها.

## 2. الوضع الحالي المثبت من الكود

| المجال | الوضع الحالي | الأثر |
|---|---|---|
| المصادقة | Manus OAuth عبر `/api/oauth/callback` | لا يوجد تدفق كلمة مرور محلي آمن؛ يجب عدم إضافة واحد داخل واجهة فقط |
| الأدوار | `user`, `supplier`, `authority`, `regulator`, `admin` في جدول `users` | تعيين المورد متاح خادمياً للمستخدم الجديد؛ الأدوار الأخرى تحتاج provisioning |
| الملف الشخصي | جدول `profiles` محدود إلى اسم المؤسسة، رقم تسجيل عام، هاتف، عنوان، ونسبة إكمال | لا يغطي NIF/NIS/RC/NIN/RIB والوثائق والإقرارات |
| API الملف الشخصي | `profile.get` و`profile.save` محميان ويتحققان من `ctx.user.id` | مناسب كأساس لاستكمال الملف، لكنه يحتاج توسيعاً وقيوداً أقوى |
| التخزين | `storagePut` و`storageGetSignedUrl` موجودان، مع فحص عام لوثائق الصفقات والعروض | يمكن إعادة استخدام طبقة التخزين بعد إضافة جدول وثائق التسجيل وقواعد وصول خاصة |
| الرفع الحالي | يقبل PDF وOffice حتى 10MB ويستخدم فحص magic bytes جزئياً | مواصفة التسجيل تطلب PDF حتى 5MB؛ يجب أن يكون لها validator مستقل لا يوسع أو يضعف القواعد الحالية |
| التدقيق | `auditLogs` موجود ويسجل العمليات الحساسة | يجب إضافة أحداث التسجيل والرفع والرفض دون تسجيل محتوى الوثائق أو الأسرار |

## 3. فجوات المواصفات والمخاطر

أهم فجوة هي أن المواصفات تفترض حقولاً قانونية حساسة وعمليات تحقق خارجية دون تحديد مصدر رسمي أو طريقة تحديث. Regex يثبت الشكل فقط ولا يثبت صحة الرقم أو ملكية الكيان. كما أن تخزين NIN وRIB والوثائق الرسمية يرفع أثر الخصوصية، ويحتاج إلى تقليل البيانات، وسياسة احتفاظ، وضبط وصول، ومراجعة قانونية قبل التفعيل.

كما أن عبارة "تشفير التخزين" لا تتحول تلقائياً إلى خاصية تطبيقية بمجرد حفظ رابط S3. يجب حفظ مفتاح تخزين غير قابل للتخمين، وعدم كشفه للعميل، وإرجاع رابط موقّع بعد تفويض خادمي. ولا يجوز اعتبار QR أو MIME أو اسم الملف دليلاً قانونياً على صحة الوثيقة.

## 4. نطاق التنفيذ المقترح

النطاق الآمن المقترح هو مسار RTL من خمس خطوات داخل بوابة المتعامل الاقتصادي بعد المصادقة، يحفظ المسودة خادمياً، ويعرض التحقق الشكلي فقط بعبارات واضحة مثل "تحقق من الصيغة" لا "تم التحقق قانونياً". تُفصل بيانات الملف عن المستخدم، وتُطبق الملكية على `ctx.user.id`، وتُحفظ الإقرارات مع نسخة النص وإصدارها وتاريخ الموافقة.

لا يُنفذ في هذه المرحلة: كلمة مرور محلية، تحقق حكومي آلي، قرار أهلية، مطابقة بنكية، أو اعتماد نهائي للوثائق. يمكن إضافة ذلك لاحقاً بعد تحديد مزود رسمي، أساس قانوني، دورة احتفاظ، وآلية مراجعة بشرية.

## 5. نموذج البيانات المطلوب مراجعته قبل migration

| الكيان | حقول مرشحة | ملاحظات الحماية |
|---|---|---|
| `operatorProfiles` | `userId`, `operatorType`, `legalName`, `wilayaCode`, `taxCenterType`, `activityCodes`, `representativeName`, `representativeQuality`, `nif`, `nis`, `rc`, `taxArticle`, `nin`, `rib`, `status`, `declarationVersion`, `declaredAt` | لا تُعاد الحقول الحساسة في استعلامات عامة؛ يجب التفكير في masking |
| `operatorDocuments` | `id`, `userId`, `documentType`, `originalFileName`, `mimeType`, `sizeBytes`, `storageKey`, `sha256`, `status`, `createdAt` | لا نخزن المحتوى في DB؛ الاسم للعرض فقط؛ المفتاح عشوائي؛ الوصول خادمي |
| `operatorDeclarations` أو حقول مدمجة | `userId`, `declarationType`, `textVersion`, `acceptedAt`, `ipHashOrRequestId` وفق السياسة | لا تحفظ إقرارات غير معتمدة قانونياً؛ لا تسجل النصوص الشخصية ضمن audit |

هذه الجداول لا تُنشأ قبل اعتماد أسماء الحقول، سياسة البيانات، ومتطلبات الاسترجاع. أي migration يجب أن تُولد وتُطبق عبر مسار Drizzle وSQL المراجع، لا عبر تعديل يدوي غير قابل للاسترجاع.

## 6. مصفوفة الوصول الأولية

| المورد | المتعامل الاقتصادي | المصلحة المتعاقدة | الإدارة المركزية | admin |
|---|---|---|---|---|
| ملفه الشخصي | قراءة/تعديل ملفه فقط | لا وصول | وصول حسب سياسة موثقة ومهمته | وصول دعم مقيّد ومدقق |
| وثائق ملفه | رفع/قائمة/تنزيل ملفه فقط | لا وصول افتراضي | وصول عند وجود صلاحية وإجراء موثق | وصول مقيّد ومدقق |
| وثائق متعامل آخر | ممنوع | ممنوع افتراضياً | ممنوع إلا بصلاحية مراجعة محددة | مقيّد ومدقق |
| الإقرارات | قبول إقراراته قبل الإرسال | لا وصول | قراءة عند الحاجة الرقابية | دعم مدقق |
| Audit logs | لا وصول | لا وصول عام | حسب نطاق الدور | قراءة مقيّدة |

## 7. الاختبارات الإلزامية قبل التنفيذ النهائي

يجب أن تغطي الاختبارات رفض NIF/NIS/RC/NIN/RIB غير المطابق شكلياً، رفض PDF الحقيقي غير المطابق أو المتجاوز لـ5MB، رفض أكثر من عدد الوثائق المحدد، منع المسار أو الاسم الخطر، منع قراءة أو تنزيل وثائق مستخدم آخر، منع تعديل ملف بتمرير `userId` مختلف، وتسجيل `upload`, `download`, `delete`, و`access_denied` بنتيجة آمنة. كما يجب اختبار مستخدم غير مصادق، مستخدم دوره `user`، وحالات عدم وجود profile أو انقطاع قاعدة البيانات.

## 8. نقطة القرار المطلوبة

يمكن البدء بتنفيذ **استكمال ملف المورد بعد OAuth** دون إعادة كتابة المنصة. أما تفعيل التسجيل العام المستقل، وتخزين NIN/RIB والوثائق الرسمية، والقول بأن التدفق "متوافق مع القانون"، فيحتاج اعتماداً قانونياً وسياسة خصوصية وموافقة صريحة على schema قبل التنفيذ. هذه الخطة لا تمنح اعتماد امتثال قانوني.
